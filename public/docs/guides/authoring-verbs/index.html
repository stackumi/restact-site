Authoring verbs

A verb is a sandboxed unit of functionality you upload and invoke over HTTP. Physically it is a wasm32-wasip2 WebAssembly component implementing the rest-act:plugin@0.1.0 contract. You write it directly in Rust, or as a JavaScript or Python file that the host interprets through a shared runner component, with no toolchain (JavaScript, Python). This page is the reference for all three. For a task-shaped walkthrough, start with Write verbs in JavaScript.

Concepts you need first

Section titled “Concepts you need first”
  • A function is pure and side-effect-free. You invoke it with GET, and its responses are safe to cache. An action has side effects and you invoke it with POST. You declare the kind at deploy time (?kind=function; leaving it out makes the verb an action), and the host enforces the HTTP method rule.
  • A verb targets exactly one WIT world, and that world is the complete list of host capabilities it can reach. Everything else is denied.
  • A verb runs with the caller’s authority, intersected with what it declared and what the target’s policy allows. It can never do something the caller could not.

See The model in one page for the full model.

The worlds

Section titled “The worlds”

The world a verb is built against is its capability manifest.

WorldImportsUse it for

plugin-composehost + gated composeA verb that invokes other verbs.
plugin-identityhost + ambient identityA verb that reads its caller.
plugin-objecthost + gated object (+ ambient identity)A verb that reads and writes its object’s data.
plugin-object-composehost + object + compose (+ ambient identity)Data access and composition.
plugin-object-eventplugin-object + gated eventA data verb that also publishes events.
plugin-object-compose-eventplugin-object-compose + gated eventData access, composition and events.
plugin-llmplugin + gated llmA verb that makes bounded model completions through a configured connector.
plugin-object-llmplugin-object + gated llmA data verb that also makes model completions.
plugin-object-compose-event-llmplugin-object-compose-event + gated llmEvery capability. The reference host binds this superset, so a verb built against any narrower world still links.

No world offers wasi:sockets, and wasi:filesystem is linked with no directories. A verb that does not import a capability cannot reach it. Targeting plugin-compose is itself the composition declaration: the host links compose only for verbs built against a world that imports it, and refuses to link it to a bare plugin verb. The identity capability is the exception. It is ambient like log: a verb imports it to read its caller, and the host links it with no grant or attenuation, because it conveys no authority the caller does not already hold.

2. Implement the Guest trait

Section titled “2. Implement the Guest trait”

The contract is invoke(payload) -> result<payload, invocation-error>. The payload is opaque bytes (list<u8>); encoding is an HTTP-layer concern. An invocation-error carries a stable machine code and a human-readable message, which the host maps onto an HTTP status + RFC 9457 Problem Details response. The code is a lower-kebab-case token of at most 64 bytes; any other code is reported as invalid-input.

Acting on object data

Section titled “Acting on object data”

A verb that only transforms its input is a function. A verb that acts on server-side data, the object it is bound to (this), does more. Target the plugin-object world and import the gated object interface:

An object path a verb names is never percent-decoded, so %2e%2e there is an ordinary name, while a . or .. segment is refused like an @ segment.

  • get(name) returns the property’s value, or None if it is absent or the caller may not read it. A read-denied property is indistinguishable from an absent one. A declared inherit property the object does not store returns the nearest ancestor’s value that the caller could read on that ancestor directly, else the declared default.
  • set(name, value) writes it, or returns an error on a write-ACL denial (forbidden), when a write-once (final) property is already set (property-final), or not-found when the object exists but the caller may not read it (the answer set gets for an absent object). A creation the host refuses fails here, at the call. Writes to the bound object are held until the verb returns and dropped if it fails. set, set-at and set-at-if refuse a name starting with $ or @ with forbidden, and a path, property name or value containing U+0000 with invalid-input before anything is buffered.
  • get-at(path, name) reads a property of another object, such as an ancestor on the inheritance chain, gated by that object’s read ACL.
  • set-at(path, name, value) writes a property on another object. It is gated exactly as a data-plane PUT /v1/<path> is, by the runs-as-caller principal, so a verb can never write what its caller could not. Each set-at commits when it is called.
  • remove(name) removes a property of the bound object and remove-at(path, name) removes one from another object (feature object-remove). Each is authorized exactly as the matching set, so a verb cannot remove what its caller could not write. Removing a property that is not set succeeds. A final property that is set returns property-final, and remove-at returns not-found when no object is stored at path. remove gives not-found when the bound object holds no data. remove is held until the verb returns, and remove-at commits when it is called (buffered under atomic-invocation).
  • shape() and shape-at(path) return an object’s shape, { properties, children, verbs }: the readable property names, the readable direct child paths and the verb names the caller’s discovery listing would show. shape() reflects committed state, so a set earlier in the same invocation is not visible yet.
  • get-bytes() and get-bytes-at(path) read an object’s binary value: the (content-type, bytes) of its content-addressed blob, or None, with the same read gate as get. The host advertises them as the object-binary feature, and the SDK exposes object::get_bytes(). Because a verb’s output is already binary, this suits read-time media transforms: an avatar:get accessor reads the stored image, transforms it and returns the new bytes. Compiled verbs and both script tiers can read binary values; a script read is capped at a quarter of the script heap (6 MiB).

Access is ACL- and scope-aware (see data properties). A property may be instance-scoped (per concrete object, the default) or shared (one value on the definition ancestor), final (write-once), and gated by per-property read and write ACLs. Everything is evaluated against the runs-as-caller principal, so a verb can never read or write what the caller could not. Capability access is gated and attenuated like composition: a verb that does not import object cannot reach any object data.

The render-html example is the reference consumer: it reads this.document (Markdown) and returns HTML.

A verb reads and writes data through the capability. The data is stored through the data plane (PUT /v1/<obj>) or by another verb’s set.

Reading the caller (identity)

Section titled “Reading the caller (identity)”

Any verb can read who invoked it through the identity interface. It exposes, read-only, the same runs-as-caller principal the host uses for authorization. Target the plugin-identity world (the object worlds import it too) and use:

Unlike object and compose, identity is ambient: it has no deploy-time grant, attenuation or ACL. It conveys no authority the verb does not already hold, because the verb runs as this caller, and the sandbox has no network to leak it through. Use it to audit, personalize or key per-user data, for example object::set("lastEditor", &object::PropertyValue::Text(who.clone())). Anonymous callers have no subject and empty roles, scopes and claims.

Composition

Section titled “Composition”

To call another verb, target plugin-compose (or plugin-object-compose) and declare every edge at deploy time:

The host enforces the declared graph (undeclared edge → 403), a shared per-request budget, depth/fan-out limits, cycle detection (508), and capability attenuation. Every edge must be declared. A function may declare calls only to other functions; an action may call either kind. See Architecture → Composition.

The verb you call may be native: a privileged primitive the platform exposes (an indexed cross-user query, a media transform) that your uploaded verb composes but cannot bypass. This is how an uploaded feed-ranking or search verb reaches ordered queries: it calls a platform verb like feed:candidates (run as you, so it sees only what you could). It is indistinguishable from calling any other verb. If you are building the platform, registering those primitives and embedding the host, see Embed restactd in a Rust app.

JavaScript (server-side, no toolchain)

Section titled “JavaScript (server-side, no toolchain)”

You can author a verb in plain JavaScript and upload it as source, with no cargo-component and no build step. The host does not compile it. It stores the script and interprets it at invoke time through one trusted, shared QuickJS runner component it ships. The script runs inside the same wasmtime sandbox under the same fuel/epoch/memory limits as any verb, and reaches the same host capabilities, so a JS verb has the same behaviors (path inheritance, object data, composition, ACLs, runs-as-caller) as a wasm one, gated identically.

When it’s absent, discovery omits text/javascript and an upload with ?lang=text/javascript returns 415. Check acceptedSourceLanguages in the discovery document (/.well-known/restact).

A source upload is syntax-checked at deploy by a compile-only parse; a script that does not parse is rejected up front with 422 (restact_code: invalid-source), carrying the engine’s message, rather than a 201 that only fails at first invoke. Runtime errors (reference errors, thrown values) still surface at invoke as script-error.

Distinguishing host errors (both scripting tiers)

Section titled “Distinguishing host errors (both scripting tiers)”

A host-capability error, such as a write-ACL denial, a final property or a failed compare-and-swap, is thrown as an ordinary catchable exception (Error in JS, RuntimeError in Python). It has no .code property. The structured code travels inside the message, delimited by SOH (U+0001), written \u0001 below:

The runners read the tag from the message of the exception that finally propagates, whatever built it (js-runner and py-runner mirror each other). A script can therefore return any code, as a Rust verb can: rethrowing the original exception, or an Error built from its message, keeps the code and the status that goes with it, and a message that carries a tag you wrote yourself is reported under that code, provided the code is a lower-kebab-case token of at most 64 bytes. Any other code, such as Not_Found or one longer than 64 bytes, is reported as invalid-input with its message kept. The code ends at the first \u0001 after it, and anything past that is part of the message. An exception without a tag is reported as script-error.

Three codes are asserted by the host:

  • delegation-bound and verb-unlinkable reach the request’s caller only when the host recorded the refusal in the same request. A composing verb can still receive either from a callee, so treat them from a composed call as a refusal like any other code.
  • verb-not-deployed means that no verb is deployed at the route the caller named. A verb that ran cannot produce it: the host answers that verb’s caller not-found and keeps the message, at every level of a composition.

When a verb composes another only if one is deployed (a veto, an extension point), catch the call and treat verb-not-deployed, and only that code, as absence. Any other failure, not-found included, can come from a deployed verb that refused, so it is a refusal:

A target built from input should be validated first. A well-formed route is answered truthfully as absent, and a target with a ., .., @ or empty path segment is answered not-found, which refuses.

Rust verbs are unaffected. In Rust the error crossing the WIT boundary is a structured invocation-error record, so e.code is a real field and the object-data examples above (InvocationError { code: e.code, … }) are correct as written. The scripting tiers cannot carry a second field across a thrown exception, which is why the code is folded into the message there.

Caveats and operational notes

Section titled “Caveats and operational notes”

The JavaScript tier is interpreted, and a few properties follow from that design:

  • Text in, text or bytes out. A script’s invoke(input) receives the request input decoded as UTF-8 (invalid bytes are replaced lossily, so binary input is not preserved). Its return value becomes the body: a Uint8Array or ArrayBuffer is sent as raw bytes, a string passes through, an object/array is JSON-stringified, and null/undefined is an empty body. Compose results are decoded as UTF-8. To accept binary input, author the verb in Rust.
  • A thrown error’s message reaches the caller. An uncaught exception surfaces as a script-error whose message text (including any QuickJS source location) is returned in the RFC 9457 detail. Don’t put secrets in error messages, and treat a script’s diagnostics as caller-visible.
  • The source is parsed on every invoke. There is no persistent bytecode cache; each invocation re-evaluates the stored script. Keep hot scripts small.
  • The runner is trusted (TCB). Every JS verb shares the one runner component, so a script’s capability surface is enforced by the host’s runtime gates (allowed_calls, property ACLs, grants, policy), not by a per-verb WIT world. The runner is built from a network-fetched WASI SDK; its content hash is reproducible only when the build is pinned (the runner’s Cargo.lock is committed and rquickjs is pinned to an exact version).

The obj and caller methods, compose, publish and llm.complete check their arguments before they call the host. A missing argument, a value that is not a string where one is required (None included), an extra positional argument or an unknown keyword raises invalid-input. If it is given it must be a string, and None is not a string: unlike set_at_if and query, which read None as omitted, compose("v", None) raises invalid-input. Caveats and operational notes

Section titled “Caveats and operational notes”

The Python tier is interpreted, so the same properties as the JS tier apply:

  • Text in, text or bytes out. A script’s invoke(input) receives the request input as a string, and its return value becomes the body: bytes are sent unchanged, a str passes through, a dict/list/number is JSON-serialized, and None is an empty body. To accept binary input, author the verb in Rust.

Language-agnostic uploads

Section titled “Language-agnostic uploads”

WASM is the substrate, but the upload declares the source language (?lang= on POST /v1/modules, Content-Type on a PUT …/code) and the host decides how to store and run it: either compiling the source to a component, or storing it and interpreting it through a host-provided runtime component:

  • application/wasm runs directly.
  • text/javascript is stored as source and interpreted by the embedded QuickJS runner (above); no per-upload compilation.
  • text/x-python is stored as source and interpreted by the embedded monty runner (above); no per-upload compilation.
  • Other source types (for example text/x-rust) would be compiled or transpiled to a component if the host has a sandboxed toolchain. The reference host has none, so these return 415.

The host stores the original source (and, for the compile path, the compiled WASM, content-addressed); GET …:verb/code honors Accept to return the source. Discovery advertises which source languages a host accepts; an unsupported one returns 415.

Deployment gotchas

Section titled “Deployment gotchas”
  • With authentication on, object binding is strict: the parent object must exist before you deploy a {id} verb under it, or the deploy answers 409.
  • A new verb is owner-only. Deploy with exec=public (or share it with PUT …/policy) for anyone else to invoke it.
  • Verbs named list, get, set, create, update and delete are accessors: they take over the matching data-plane requests on their object instead of being ordinary verbs.
  • Delete a {id} verb with DELETE /v1/<pattern-with-{id}>:verb/code, using curl -g so the braces survive.
