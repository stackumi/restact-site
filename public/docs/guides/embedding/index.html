Embed restactd in a Rust app

Use restactd as a Rust library: register native verbs and custom HTTP routes in your own binary, and let users extend your platform with uploaded verbs.

This page is for platform builders. Authoring verbs is written for the people who upload verbs to your platform.

The two-tier model

Section titled “The two-tier model”

A REST:ACT application has two kinds of code, with a hard trust boundary between them:

Trusted platformUntrusted experience layer
Who writes itYou (the operator)Your users / third parties
What it isNative Rust verbs + custom HTTP routes, compiled into your binarySandboxed verbs uploaded over HTTP (wasm / JavaScript / Python)
TrustTCB, full authority of the processConfined to what its world imports and what the caller could do
How it runsA host functionWasmtime sandbox, fuel/epoch/memory metered
Examplesfeed:candidates, a WebFinger route, federation deliverya user’s custom feed ranking, a profile widget, a redaction filter

The platform exposes primitives; users compose them. A native feed:candidates verb does the privileged, expensive work (an indexed query over everyone’s posts, run as the caller); an uploaded timeline:rank verb a user wrote calls it and re-orders the result however they like. The user’s code never touches the database directly and is bounded by fuel, but the behavior is theirs. It runs with that user’s authority, so every read is checked against what the user may read.

Note

If everything your platform does can be expressed as uploaded verbs over object data, you don’t need to. Run the stock restactd binary and deploy verbs to it. Embed when the platform itself needs to do something untrusted code can’t be given directly: talk to another server (federation, outbound HTTP), serve a non-/v1 URL (WebFinger, an ActivityPub actor document), or expose a privileged primitive (a cross-user indexed query) as a verb users may compose but not bypass.

The embedding API

Section titled “The embedding API”

The host is a Rust library, restactd, as well as the stock restactd binary. Your application is its own crate that depends on it.

restactd::run(builder) is the embedding entry point: it opens the configured backends (the same RESTACT_DATA_DIR / RESTACT_DATABASE_URL / isolation / auth env vars as the stock host), applies your HostBuilder, bootstraps, and serves. The stock binary calls restactd::cli::main(), which parses --help and --version and then calls restactd::run_default(). run_default() is run(configure_host()) with the default extension set, and both return anyhow::Result<()>. Both print the build line on stdout before the host’s own boot output (a process-isolation worker never prints it). Your binary keeps every operational knob in Configuration. Embedding only adds native verbs and routes and, opt-in, the reference host’s own built-in static site (HostBuilder::with_builtin_site()). A default HostBuilder never mounts it, so GET / and the other site paths are free for your own routes.

HostBuilder

Section titled “HostBuilder”

A builder collected before serving. Four chainable methods:

with_builtin_site() mounts the reference host’s demo static site and its repo_doc fallback, which serves several top-level directories of the process’s working directory read-only. That is a disclosure surface, not something to turn on casually off-box. It’s idempotent, takes no argument, and there’s no disabling counterpart: off is the default, so a plain HostBuilder::new() never mounts it and GET //GET /index.html/etc. are ordinary custom-route territory for your own register_route calls.

HostBuilder is Clone and cheap to clone (handlers are Arcs). That matters for process isolation. Under RESTACT_ISOLATION=process the per-request worker re-execs your binary and re-runs main, which rebuilds the same builder, so your native verbs resolve identically in the parent and the worker. The only rule: build the HostBuilder deterministically (the worker must produce the same registrations the parent did). Reading env vars to decide what to register is fine (the worker inherits them); registering based on a random seed or wall-clock is not.

Native verbs

Section titled “Native verbs”

A native verb is the trusted analogue of an uploaded one. It is resolved, composed, accessor-dispatched, run-as-caller, policy-checked, and quota’d exactly like any verb. It’s just backed by a Rust function instead of a wasm component, and is protocol-invisible (a client cannot tell). It consumes no fuel (it’s TCB code) and is bounded by wall-time + the per-tenant quota.

NativeVerbSpec carries everything a deployed verb would: kind, policy, produces, data_properties, runs_as_owner, and the capability grants (granted_data / granted_compose / granted_event). The grants are deny-by-default: a verb that doesn’t set granted_data provably can’t reach object data, same as an uploaded verb whose world doesn’t import object.

The handler receives a NativeCtx, the trusted mirror of the sandbox’s host state, reusing the identical capability cores so native and wasm behavior match:

NativeCtx methodWhat it does
input()the request payload bytes
get / set / get_at / set_atobject-data capability (ACL- & scope-aware, run-as-caller)
get_bytes(path)read a binary object value (content_type, bytes) (binary values)
query(prefix, order_by, descending, predicate, limit, cursor)the ordered collection query, ACL-filtered as the caller
compose(verb, input)invoke another verb under the shared attenuated budget
publish(topic, name, data)emit an event (gated by granted_event); name 1-128 bytes, no ASCII control chars, and not onCreate/onChange/onDelete/gap (forbidden); data empty or one JSON object with no top-level $ member, else invalid-input; the host adds a $publisher member naming the verb’s route; topic at most 1024 bytes (invalid-input); data over 64 KiB stamped, or over 4 MiB published in one invocation, is 413 object-too-large
subject / is_anonymous / roles / scopes / groups / claimthe run-as-caller identity
accept / header / method / set_content_typethe request context, for representation negotiation
block_on(future)drive an async future to completion (e.g. an outbound HTTP call) from the synchronous handler
object_path()the bound object’s path (for accessor verbs)

Native verbs are defaults registered by the embedder. An uploaded verb at the same (object, verb) key takes precedence over the native, and removing the upload brings the native back. Precedence compares the route patterns first, so an upload at a more specific pattern outranks a native at a less specific one, and a native at a more specific pattern outranks an upload at a less specific one. This lets a platform ship a built-in such as timeline:rank that each user can replace on their own object.

Who may upload follows the usual deploy rules: the object’s owner under a coupled binding mode. At the native’s exact key the native’s own write policy also applies. A native registered with Policy::default_for("anonymous"), as the examples are, admits no named user there on an authenticated host.

Custom routes

Section titled “Custom routes”

Native verbs live under /v1. To serve URLs the protocol doesn’t define (a WebFinger endpoint, an ActivityPub actor document or inbox, an OAuth callback), register a plain HTTP route:

The handler is a synchronous Fn(RouteContext) -> Result<RouteResponse, RouteError> run on the blocking pool (so it may block_on outbound I/O without starving the reactor); an Err(RouteError) maps to an application/problem+json response, so ? works for failures. RouteContext gives it the method, path, raw query, headers (lowercased; rc.header("user-agent")), body bytes, and a RouteExecutor (rc.exec), a narrowed read/query/invoke handle (object_get/object_put/object_get_blob/object_put_blob/query_objects/ invoke/resolve_kind, each taking an explicit &Principal). It deliberately does not expose the control-plane methods (reset/remove/set_policy/…), so a custom route can’t reach them by construction. object_put_blob refuses a content type that is not exactly one media type with invalid-input; an empty one is stored as application/octet-stream. The host authenticates the request before your handler runs: a request that presents a bearer or identity header which fails verification gets the same 401 as /v1 and never reaches the handler, and a request with no credential runs as anonymous. The host owns Authorization: Bearer on custom routes, including on a host with no auth configured (any bearer gets 401), so a route cannot accept its own bearer scheme; other schemes (Signature, Basic) reach the handler. Federation routes then verify their own HTTP signatures and choose the principal; a public WebFinger uses Principal::anonymous. A register_route path at or under /v1 would shadow an object, so the host refuses to start and names the path. RouteResponse has ok(content_type, body), json(body), status(code, msg), and .with_header(name, value). Custom routes are mounted only in the parent’s router; a (path, method) pair that collides with a built-in route panics at startup (an operator error, surfaced loudly). The built-in site paths are free custom-route territory unless with_builtin_site() is on, in which case they collide like any other built-in.

The enablers

Section titled “The enablers”

Four capabilities make a data-shaped application (a feed, a profile, media) buildable.

The query primitive (collections)

Section titled “The query primitive (collections)”

Object data is more than key/value lookups: the store has an ordered, prefix-scoped, predicate-filtered, cursor-paginated query. A native verb reaches it via ctx.query(...), and it is the foundation of any collection: a timeline, an outbox, a search result, a leaderboard. Uploaded verbs reach the same primitive through the object capability’s query (feature verb-object-query), which returns an ACL-filtered, cursor-paginated page under a host-clamped per-call cap. The separate object-query token gates only the GET /v1?filter=/read_mask= listing refinement.

ACL filtering happens above the store (Executor::query_objects): the listing is always ⊆ what the caller could read, with honest keyset pagination (it over-fetches so a page is never silently truncated by ACL drops). On the PostgreSQL backend this is a real indexed SQL query with a (order, path) keyset, not a scan. Uploaded verbs can call object.query directly, or compose a native query verb you expose (e.g. feed:candidates) when the platform should control exactly what is queryable. The same primitive backs GET /v1 object listing (order_by-by-path, filter=, pageToken).

Tip

Paginate via the cursor and don’t infer “done” from a short page. To bound per-request work (a low-privilege query over a large store would otherwise scan everything), query() caps the candidates it examines per call; if it hits the cap it returns a short page plus a continuation cursor. So a next of Some(cursor) means “call again from here,” even when fewer than limit rows came back; only next == None means the collection is exhausted.

Binary / media values

Section titled “Binary / media values”

A property’s value can be binary (an avatar, a header image, post media), stored as a content-addressed blob with a tiny $blob reference in the attribute map, not base64 in JSON (features binary-values + object-binary):

  • Data plane: PUT /v1/users/alice/avatar with Content-Type: image/png stores the bytes; a GET serves them back with that content type + a content-hash ETag. The object’s representation is the bytes. Internally the dedup’d blob store holds them and the object keeps a tiny $blob reference, so the per-object size cap bounds the reference, not the media.
  • Verbs: a native verb reads bytes with ctx.get_bytes(path); an uploaded wasm verb with the additive object.get-bytes / get-bytes-at methods (SDK: object::get_bytes()).

Because a verb’s output is already binary, the canonical pattern is a read-time transform: an avatar:get accessor that reads the stored image, transforms it by caller/time/locale, and returns the new bytes, with no second stored copy and no write capability needed. (Verb-persisted binary, set-bytes, and streaming are not available.)

Run as the caller

Section titled “Run as the caller”

Every capability, native or uploaded (query, get, set, compose), is evaluated against the caller’s principal. A native feed:candidates invoked by Alice reads only what Alice could read; the same verb invoked by Bob sees Bob’s view. This is why you can safely let users upload feed/search/view logic that composes your primitives: their code inherits their authority and can never exceed it. (A platform verb that must act with its owner’s authority instead (for example a moderation hook) opts in with runs_as_owner, setuid-style.)

Worked example: a social platform users can reshape

Section titled “Worked example: a social platform users can reshape”

Here is a motivating case: an ActivityPub server that interoperates with Mastodon, whose differentiator is that users shape their own experience: custom feed ranking, custom search, custom views of their own data.

The split: the federation engine (HTTP signatures, delivery, inbox processing, key management) is trusted native code in your binary (it makes outbound calls and owns crypto, which untrusted code can’t be handed). The experience layer (how a timeline is ranked, what a search does, how a profile renders) is untrusted, user-uploaded verbs that run as the user and compose your primitives.

Now a user makes the platform theirs without you shipping anything. They upload a verb (JavaScript, no toolchain) that re-ranks the native candidates:

The same shape gives you user-defined search (search:run composing a native posts:query), custom views (an accessor verb that reshapes the user’s own object data), and reactions (an action that writes a shared-scoped count). Every one of them is fuel-bounded and runs with the user’s authority, so every read is checked against what the user may read.

Where each enabler lands: feed:candidates/posts:query need the query primitive; avatars/media need binary values; the actor document negotiates application/activity+json vs HTML via negotiation; per-user scoping is run-as-caller; the federation engine reaches the network from native handlers via block_on. An untrusted verb’s one outbound path is the llm capability; the mediated outbound call (see Configuration → Mediated egress) is available only to native verbs and embedder routes. In this architecture the federation engine’s egress stays trusted native code.

Operating an embedded host

Section titled “Operating an embedded host”

An embedded host is configured and secured exactly like the stock one. It is the stock host plus your registrations. So everything in Configuration applies unchanged: durable storage (RESTACT_DATA_DIR) or the active-active PostgreSQL backend (RESTACT_DATABASE_URL), authentication (RESTACT_JWT_SECRET / OIDC / trusted headers), per-request process isolation (RESTACT_ISOLATION=process; remember the deterministic-builder rule above), quotas, CORS, and the binary-blob cap (RESTACT_MAX_BLOB_BYTES). Run RESTACT_DEMO_NATIVE=1 against the stock binary to see a live native verb (sys:objects), a native query verb (sys:query), and a demo custom route (/.well-known/demo-webfinger) before writing your own. These are the same registrations scripts/native-test.sh exercises on both backends.
