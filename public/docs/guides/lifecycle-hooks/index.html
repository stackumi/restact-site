Lifecycle hooks

A lifecycle hook is a verb that restactd runs for you when an object is created, changed or deleted. This guide deploys three hooks that write an audit trail, then shows what runs the hook, how failures are handled and how to switch hooks off.

Prerequisites

Section titled “Prerequisites”
  • A running restactd with the JavaScript tier (see Install and Quickstart). The examples use the default http://localhost:8080 with no authentication configured.
  • curl.

1. Write the hook

Section titled “1. Write the hook”

What just happened

Section titled “What just happened”

After each data-plane write, the host looked up a verb with the reserved name on the object, walking up the ancestry and the {id} pattern, and invoked it synchronously. The event payload has three members:

MemberValue
eventonCreate, onChange or onDelete
objectthe concrete path of the object that changed
subjectthe caller who made the write, for information only

Hooks also fire when a verb changes object data with obj.set, obj.setAt, obj.remove or obj.removeAt, not only for HTTP requests. A hook that writes an object which has its own hooks can start a chain; the host stops a chain at depth 4.

The discovery document advertises the behaviour as service.lifecycleHooks: true, the lifecycle-hooks feature, and "role": "lifecycle-hook" on each hook verb.

Whose authority a hook runs with

Section titled “Whose authority a hook runs with”

A hook runs as the user who deployed it, not as the user whose write triggered it. The hook’s owner supplies the identity, the object permissions and the quota. This lets a hook write to a place the triggering user cannot.

To see it, start a host with authentication (Add authentication); it uses strict binding, so create the parents first. As Alice, create notes, and create audit so that only its owner may write it:

Deploy the three hooks as Alice (add -H "Authorization: Bearer $ALICE" to the deploy command from step 2), then let Bob create notes/b2. The hook runs as Alice and writes the audit entry; the entry names Bob as the subject:

A direct write by Bob to audit is refused with 403, because only Alice may write there. A hook can never do more than its owner could do.

Objects the hook’s owner cannot read

Section titled “Objects the hook’s owner cannot read”

A hook fires only if its owner could read the object it fired for. If the object’s $policy leaves the owner out, the hook is skipped: it does not run, no ancestor’s hook runs in its place, and nothing is charged to the owner’s quota. The check uses the owner’s own identity, not the writer’s, and not any role, group or scope the owner’s token happens to carry. For onDelete it uses the object’s policy as it stood just before the delete. The server logs one line naming the hook’s route, not the object, with reason=not-readable.

Failure behaviour

Section titled “Failure behaviour”

Hooks are best-effort. If a hook throws, restactd logs the failure and keeps the write that triggered it. Deploy a hook that always fails and write an object it covers:

Do not use a hook to enforce a rule that must reject a write. A hook cannot veto the write that triggered it.

Turn hooks off

Section titled “Turn hooks off”

Set RESTACT_LIFECYCLE_HOOKS=off (also 0 or false) when you start restactd:

Deployed hooks stay deployed but no write fires them. Discovery reports service.lifecycleHooks: false and omits the lifecycle-hooks feature. You can still call a hook directly, as with any action: POST /v1/notes/1:onCreate.
