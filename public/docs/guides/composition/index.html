Compose verbs

One verb can call another and use its result. The host runs the whole call tree under one shared budget, with the original caller’s authority at every step, and turns a failure anywhere in the tree into a defined response.

This guide builds a small chain, then shows how the budget, the caller’s identity and failures travel through it.

Prerequisites

Section titled “Prerequisites”
  • A running restactd on localhost:8080 with the JavaScript tier. The same calls work from Python and Rust verbs.
  • For the identity step, a host with HS256 authentication configured. Add authentication shows how to set it up and mint tokens.

The call graph is part of the deployment. A verb that calls something it did not declare is refused when the call happens:

Functions and actions follow different rules. A function has no side effects, so a function may only declare calls to other functions. Declaring a call from a function to an action fails at deploy time, once the action exists:

An action may declare calls to both kinds. This is what keeps GET safe: a function’s whole tree is free of side effects.

One budget for the whole tree

Section titled “One budget for the whole tree”

Every verb in a call tree draws from the same pool of compute and the same wall-clock deadline, so a request cannot get more of either by splitting work across verbs. Memory is different: each verb instance has its own memory cap. The defaults are in the discovery document under defaultCapabilities: 200 million compute units, 2 seconds and 32 MiB.

This pair makes the point. bud:burn loops input times, and bud:tree calls it four times:

One burn call at 20000 fits in the budget. Four of them in one tree do not. The exact threshold depends on the script and the runner. Two structural limits apply too: a call chain may be at most 8 verbs deep (the entry verb counts), and one verb may make at most 16 compose calls per invocation. Past either limit the host answers 508.

fan:many calls the leaf verb input times in a loop. A call that would close a cycle is refused with the same status, 508, and a detail such as cycle detected: 'loop:a' is already on the call stack.

The caller’s identity follows the chain

Section titled “The caller’s identity follows the chain”

Each verb in the tree runs as the original caller, not as the verb above it and not as the verb’s owner (unless the verb is deployed with runs_as=owner; see Identity and authority). A callee cannot see or change anything the caller could not.

What happens when a callee fails

Section titled “What happens when a callee fails”

A failure inside a callee comes back to the caller as an exception (compose throws in JavaScript, raises RuntimeError in Python, returns Err in Rust). You can handle it, or let it propagate.

When a callee’s error reaches the top uncaught, the caller of the whole chain gets that error’s status and detail, such as 403 for a refused write or 422 for a script error. If the callee’s failure is a host capability error, the message carries a code between SOH characters; the JavaScript guide shows how to read it. Do not put secrets in error messages: they travel back through every layer.

Writes follow the consistency level of the host. With RESTACT_CONSISTENCY=atomic-invocation, a failure that reaches the top of the tree discards the writes of every verb in it, and a callee failure that its caller catches discards only that callee’s writes. See Store and query object data.
