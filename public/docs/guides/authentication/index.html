Add authentication

By default restactd has no authentication: every caller is anonymous and can do anything. This guide turns on authentication with signed tokens, shows two users getting different results from the same verb, and then covers verifying tokens from a real identity provider and running behind an authenticating proxy.

Prerequisites

Section titled “Prerequisites”
  • restactd built from source with the JavaScript tier (Install).
  • curl and openssl. Node is needed only for the OIDC section.

Pick a mode

Section titled “Pick a mode”

restactd resolves the caller in a fixed order and uses the first source that identifies someone:

  1. A trusted identity header set by your proxy, if RESTACT_TRUSTED_IDENTITY_HEADER is configured.
  2. An OIDC bearer token verified against your identity provider’s keys, if RESTACT_OIDC_* is configured.
  3. An HS256 bearer token signed with a shared secret, if RESTACT_JWT_SECRET is configured.
  4. Anonymous.

A bearer token or identity header that fails verification is refused before any handler runs, on /v1 and on custom routes alike: 401, or 403 for a delegated token on a custom route. It is never served as anonymous.

ModeUse it for
HS256 (RESTACT_JWT_SECRET)Local development, tests and service-to-service tokens you mint yourself.
OIDC/JWKS (RESTACT_OIDC_*)Production with an identity provider that publishes signing keys.
Trusted header (RESTACT_TRUSTED_IDENTITY_HEADER)Production behind a proxy that already authenticated the user.

Mint a test token

Section titled “Mint a test token”

An HS256 token is a signed JWT. restactd token mint signs one for a subject you name. It reads the secret from RESTACT_JWT_SECRET in its own environment, never from an argument, so run it where the secret is set (your shell, or docker exec into the container):

Inside the container image, restactd is on the path: docker exec <container> restactd token mint --sub alice. The container needs RESTACT_JWT_SECRET in its environment, which it has when you passed it to the host.

--role, --group, --scope and --claim K=V repeat. The token lasts one hour unless you pass --ttl (90s, 5m, 12h, 7d; the longest is 30d). --json prints {"token": ..., "expiresAt": ...}, with expiresAt in Unix seconds. The command refuses a blank subject, one with leading or trailing whitespace, one with control or format characters (zero-width and bidirectional marks included), anonymous, a subject starting client:, and claim names the token already uses (sub, exp, aud and the like).

The claims restactd reads:

ClaimBecomes
subthe caller’s subject
rolesan array of roles
scopea space-separated list of scopes
groupsan array of groups
any other scalaravailable by name through caller.claim

A token whose subject is exactly anonymous is refused, because that name is reserved for unauthenticated callers.

What just happened

Section titled “What just happened”

Every verb runs as the caller who invoked it. The host checks the verb’s execute policy against the caller, and the verb can then read or write only what that caller could. caller is read-only and grants nothing the caller does not already hold. Identity and authority explains the model.

Verify tokens from an identity provider

Section titled “Verify tokens from an identity provider”

For production, have restactd verify RS256 or ES256 tokens against your provider’s published keys. Set all three of the following. All three variables are required: setting only some of them (or any to an empty value) refuses boot and names what is missing. The JWKS URL must be https:// (plain http:// only to a loopback address). Confirm the boot line auth: OIDC/JWKS verification enabled ….

VariableMeaning
RESTACT_OIDC_ISSUERThe expected iss claim.
RESTACT_OIDC_JWKS_URLThe provider’s JWKS URL. It must be https://, except for a loopback address in development. Redirects are not followed.
RESTACT_OIDC_AUDIENCEThe expected aud claim. Audience checking cannot be turned off.

Optional settings: RESTACT_OIDC_JWT_HEADER (the header carrying the token, Authorization by default), RESTACT_OIDC_SUBJECT_CLAIM (default sub) and RESTACT_OIDC_JWKS_TTL_SECS (key cache lifetime, default 3600).

The signing algorithm is taken from the key (RSA means RS256, EC P-256 means ES256), never from the token header, so alg: none and algorithm-swap tokens are rejected. exp, nbf, iat, iss and aud are all checked. The host fetches the key set over HTTPS, so allow outbound access to your provider on port 443.

Tokens pass through the same checks as HS256 ones. A token with a damaged signature answers 401 with OIDC token verification failed. When OIDC and HS256 are both configured, an OIDC token is tried first, and a token that is not an OIDC token falls through to HS256 so service tokens keep working. Keep the two sets of subject names apart, because both produce plain subjects and the same name is the same person.

Hand out a path-scoped sub-token

Section titled “Hand out a path-scoped sub-token”

A sub-token lets you give someone, or a browser page, read access to one part of the object tree without handing over your own credential. It is signed with the HS256 secret, so it exists only on a host that has RESTACT_JWT_SECRET set; an OIDC-only or trusted-header host has none. Discovery lists the feature as path-scoped-tokens, and RESTACT_SUB_TOKENS=off removes the route.

Any authenticated caller can mint one, with their own token or one from restactd token mint. An anonymous caller gets 401. A sub-token cannot mint another, and neither can a principal acting through a delegated grant or the actor of a live grant it has exchanged, even with its own bearer token (403). On a host without RESTACT_JWT_SECRET, the route is mounted but an authenticated OIDC or trusted-header caller gets 503.

The prefix has to be an object that exists, so create it first if it does not:

FieldMeaning
prefixRequired, a non-empty object path. The token covers that object and everything below it, matched on whole path segments: notes/shared covers notes/shared/a but not notes/shared-old.
ttl_secondsOptional. Defaults to 300 and is clamped to between 1 and 900.

You can mint a token only for a prefix that exists and that you can read yourself. A prefix that is absent and one you cannot read both answer 403. A caller may make 30 mint requests a minute, counted in a fixed 60-second window per host process. A request counts once it passes body and prefix validation, so the read-check 403 and the no-secret 503 count, while a 401, 400 or delegation 403 does not; past that the host answers 429 with Retry-After: 60.

The token does one thing: a GET or HEAD of the stored value of an object under the prefix. It cannot invoke a verb, read ?meta= or a verb’s management pages, subscribe to events, list collections, write, deploy, or reach any route an embedding application adds. Outside the prefix the answer is 403.

A page running in a sandboxed frame sends Origin: null. When RESTACT_CORS_ALLOW_ORIGIN is set, the host accepts that origin for a valid sub-token on a plain GET or HEAD, so such a page can read the object; with CORS off, browsers block the read. The route is listed in the HTTP API reference.

Run behind an authenticating proxy

Section titled “Run behind an authenticating proxy”

If a proxy such as oauth2-proxy, Authelia or a cloud access gateway has already authenticated the user, restactd can take the identity from a header:

RESTACT_TRUSTED_SCOPES_HEADER works the same way for scopes. The headers carry the subject and lists: roles and groups may be separated by commas or spaces, scopes by spaces only:

Caution

restactd does not check a signature on these headers. Any client that can reach restactd directly can claim any identity by sending the header. Use this mode only when the proxy is the sole route to restactd, and the proxy removes any copy of the header the client sends. Keep restactd bound to a private address or network so nothing bypasses the proxy. Prefer OIDC when your provider supports it.

At startup the host logs which header it trusts, so the mode is never silent.

Keep a subject namespace for your own services

Section titled “Keep a subject namespace for your own services”

If you mint HS256 tokens for your own services under a naming scheme such as agent:<workspace>:<name>, reserve the prefix so an identity provider or proxy can never produce it:

A subject from OIDC or the trusted identity header that starts with a reserved prefix gets 401; your HS256 tokens are unaffected. The same two sources also refuse subjects containing :, whitespace or an invisible format character. If your provider issues colon subjects on purpose (GitHub Actions, Kubernetes service accounts, SPIFFE), set RESTACT_EXTERNAL_SUBJECT_ALLOW=colon; the reserved prefixes still hold. Control characters in a subject are refused on every path.

Check your setup

Section titled “Check your setup”
  • A request without a token can read but not write. Verify with the PUT shown in step 1.
  • RESTACT_BIND defaults to loopback. Set 0.0.0.0:8080 only when something in front of restactd enforces authentication, or when RESTACT_JWT_SECRET or OIDC is set. A non-loopback bind also needs RESTACT_ALLOWED_HOSTS (the host names clients use), or the host refuses to start.
  • Store RESTACT_JWT_SECRET in your secret manager and rotate it like any signing key. Whoever holds it can mint a token for any subject.
