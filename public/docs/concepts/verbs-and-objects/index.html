Verbs, objects and routes

Everything restactd serves is an object at a path. An object holds data, and verbs attach to objects or to patterns of objects. This page covers how paths resolve to verbs and how object data behaves.

Paths

Section titled “Paths”

The colon separates the object from the verb. Verb names are camelCase and avoid the standard method names. A verb is itself addressable: /v1/animals/dogs/fido:noise/code is its source or component, /policy holds its owner and access policy, and /meta its descriptor: the kind, limits and declared capabilities.

Functions and actions

Section titled “Functions and actions”
FunctionAction
Side effectsnoneallowed
HTTP methodGETPOST
Cacheableyes (ETag, 304 on a match)no
Compositionmay call only functionsmay call functions and actions

You choose the kind at deploy time with kind=function or kind=action. If you leave kind out, the verb is an action. A function cannot write object data, publish events or call an action. The host refuses each of those at runtime with 403 forbidden-side-effect. Function results carry Cache-Control: private, no-cache and Vary: Authorization because the output can depend on the caller.

An action can take an Idempotency-Key header, and when the caller is authenticated a retried request with the same key replays the first result instead of repeating the effect. Anonymous callers get no replay. Long-running actions may return 202 with a Location header to poll. See HTTP API.

Bound verbs and route patterns

Section titled “Bound verbs and route patterns”

A verb is deployed at a route, and the route decides which objects it answers for.

BindingRouteMatches
Entitydocs/{id}:wordCountdocs/42:wordCount, any one segment in place of {id}
Collectiondocs:bulkImportdocs:bulkImport, and by the lookup below any object under docs
Unbound:pingthe service root, /v1/:ping

When you invoke docs/42:wordCount, the verb runs bound to the concrete object docs/42. Resolution also walks up the path: :ping invoked on docs/42 looks at docs/42, then docs, then the root, and runs the first match, still bound to docs/42. If two routes both match at one level, they are compared segment by segment from the left, and at the first segment where one has a literal and the other a {id}, the literal one wins, regardless of deploy order (ws/1/{id} beats ws/{id}/pages).

A verb can read the concrete path of the object it is bound to, so it can address itself without being told its own name. See the path function in wit/object.wit.

Tip

In curl, pass -g or encode the braces as %7Bid%7D, or curl treats {id} as a glob.

Object data as a plain noun

Section titled “Object data as a plain noun”

A path without a verb is the object’s data. It is a JSON object of typed properties (any JSON value; a top-level null removes one).

PUT merges the fields you send. GET returns the properties you are allowed to read. A missing object is 404. The same data is what a verb sees through its object capability, so a verb and a client are two ways to reach one store. A non-JSON PUT stores binary content, served back with its content type. The first writer of an object becomes its owner. Properties can be declared with read and write rules and a write-once flag. See Store and query object data.

Collections

Section titled “Collections”

GET /v1 lists the objects you can read, ordered by path and paged with pageSize and pageToken. filter=kind=note keeps objects whose readable kind property equals note, and read_mask=title,kind adds those properties to each entry. A verb can read a page of objects under a prefix with the query function of the object capability. Both honour the same read rules as a direct GET, so a listing contains only what you could fetch one by one.

Binding modes

Section titled “Binding modes”

The binding mode decides whether an object and its verbs are coupled. The operator sets it with RESTACT_OBJECT_BINDING, and discovery reports it as service.objectBinding.

ModeDeploying a verb on an object that does not exist
implicitallowed; object and verbs are independent
auto-createallowed; the object is created, owned by the deployer
strictrefused with 409; create the object first

In the coupled modes (auto-create and strict) you also need to own an existing object to deploy a verb onto it, and DELETE /v1/<obj> removes every verb anchored at the object (those bound to it and the {id} patterns beneath it) along with its data. If any of them isn’t yours to remove, the whole delete is refused with 403. A server with authentication configured defaults to strict; one without defaults to implicit. See Configuration.

Accessor verbs

Section titled “Accessor verbs”

A few verb names are reserved to mediate the data plane: get, list, create, update, set and delete. If you deploy a verb with one of these names on an object, a matching request for that object’s data (a GET, a PUT and so on) runs your verb instead of reading or writing the store directly. This lets an object present a computed representation, or validate and transform writes, while clients keep using plain GET and PUT. The accessor runs with the caller’s authority like any verb. The lifecycle names onCreate, onChange and onDelete are also reserved: they run after a write or delete commits. See Lifecycle hooks.

Native verbs

Section titled “Native verbs”

A verb can also be a function in the host’s own Rust code, registered by a program that embeds restactd. A native verb is addressed, composed and authorised exactly like an uploaded one, and it is trusted code, so it consumes no fuel. An uploaded verb at the same route replaces the native default, and removing the upload brings the native one back. See Embed restactd in a Rust app.
