Identity and authority

Every request is made by a principal, and a verb acts with that principal’s authority. This page covers who the principals are, how access rules are written, and what changes once you turn authentication on.

Principals

Section titled “Principals”

The host resolves the caller from the request through an ordered chain: a trusted identity header from a proxy (if configured), a verified OIDC bearer token (if configured), an HS256 bearer token, and finally anonymous. The first source that yields a named principal wins. A principal has a subject, and optionally roles, scopes and groups. Setup is in Add authentication.

With no authentication configured, every request is the anonymous principal. That is meant for local development on loopback. The subject name anonymous is reserved, and a credential that claims it is refused.

Run as the caller

Section titled “Run as the caller”

A verb executes as the principal that called it. Its effective authority is the intersection of:

  • what the caller is allowed to do,
  • what the verb declared it needs (its imports and call graph),
  • what the target’s policy allows.

A verb therefore cannot do anything the caller could not do directly. When verbs call verbs, each callee runs with at most the caller’s authority. Cost is charged to the caller.

A verb can read who is calling through the identity capability: subject, is-anonymous, roles, scopes, groups and individual token claims. That lets it key data per user or record an audit line. It cannot change them.

Running as the owner

Section titled “Running as the owner”

A verb deployed with ?runs_as=owner is the exception. It runs with its owner’s subject-only authority, like a setuid program. The execute check still runs against the real caller, and the bill still goes to the caller. Use it for a privileged operation the platform deliberately exposes, such as a write that only the owner could otherwise perform. Lifecycle hooks work the same way: they run as the principal who deployed the hook, not as the user who triggered it.

Policies and matchers

Section titled “Policies and matchers”

Verbs, individual object properties and whole objects each carry an access policy. A policy maps actions (read, write, execute, manage) to lists of matchers. A request is allowed if any matcher in the list admits the principal.

MatcherAdmits
publiceveryone, including anonymous callers
ownerthe object’s or verb’s owner
sub:<id>one subject
role:<r>principals holding a role
group:<g>principals in a group
scope:<s>principals whose token carries an OAuth scope
claim:<k>=<v>principals whose token has that claim value

A new verb defaults to owner for execute, read and write, so on a host with authentication only its deployer can run it until the policy is widened (for example {"execute":"public"} on …:verb/policy). The first writer of an object becomes its owner, and a verb’s deployer owns the verb. Object-level $policy sets a baseline read, write and delete rule for an object, and property ACLs can narrow it. A property can also be declared write-once. For per-instance rules, prop:<name> admits the subject named by that object’s own <name> value. The routes for editing policies are in the HTTP API.

Who owns a new object

Section titled “Who owns a new object”

The first principal to write an object at a path where nothing exists owns it. Ownership attaches to the path being created, not to its neighbours: a principal that creates ws/notes beneath someone else’s ws owns ws/notes, as long as the policy that applies at that path lets it write there. The default policy on a path with no governing policy admits any authenticated principal. A parent does not hand out a separate right to create beneath it, and the owner of ws has no say over who creates ws/notes unless ws is an anchor.

On a host shared by several tenants this means a child path under another principal’s object can be taken by whoever writes first. To keep that in your hands:

  • Create the top-level containers yourself, as the operator, before users arrive, and create each container before the objects that belong under it.
  • Turn on RESTACT_POLICY_INHERITANCE and mark the containers as anchors: an object whose $policy carries "inherit": true governs every path below it that has no nearer anchor. A first write under an anchor is admitted only when the anchor’s write policy admits the writer, so an anchor with "write": ["owner"] lets only its owner create beneath it.
  • Turn on RESTACT_GOVERNED_CREATION as well. A creating write outside every anchor is then refused 403 unless it carries a $policy of its own, so no one can quietly take an ungoverned path. Verbs can never write $policy, so a verb that creates objects outside an anchor is refused too.
  • Use ids that cannot be guessed where a path would otherwise be predictable.

A dedicated permission to create beneath an object, granted by the object’s owner, is planned. Until it exists, the steps above are the way to control who may create where. See Configuration for both variables.

Anonymous callers

Section titled “Anonymous callers”

Once any authentication is configured (a JWT secret, OIDC, or a trusted identity header), anonymous callers can read and invoke public actions but cannot mutate. Deploys, verb management writes, and data-plane PUT, PATCH and DELETE answer 401 for them. A verb’s execute policy still decides whether an anonymous caller may invoke it.

With no authentication configured, the deployment is open on purpose: every caller is anonymous and therefore the owner of anything anonymous created. Do not expose such a host beyond loopback.

Who may define a verb

Section titled “Who may define a verb”

Replacing the code of an existing verb is governed by that verb’s write policy. Defining a verb at a new route depends on the binding mode (see Verbs, objects and routes): under the coupled modes you must own the object you deploy onto. On a host with auth configured, every verb at the service root or on a leading-wildcard route is limited to the operator named by RESTACT_ADMIN_RESET. The full rules are in Configuration.
