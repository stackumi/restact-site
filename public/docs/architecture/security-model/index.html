Security model

restactd runs code that strangers upload. The design assumes from the first request that an upload may be malicious, and each layer below limits what such a verb can do. This page describes what the server enforces and where.

Threat model

Section titled “Threat model”

The assets are the host process, other tenants’ data and compute, and the secrets the host holds. The attacker is a caller who can upload a verb (where policy allows it) and invoke verbs, and who controls the verb’s code, input and the data it writes. The attacker has no access to the host’s operating system, the network between operator and server, or the operator’s configuration.

The trust boundary is the Wasmtime sandbox. Everything inside it is untrusted: uploaded components, and the scripts that run in the shared runners. Everything outside it is the trusted computing base.

Layers

Section titled “Layers”

Sandbox

Section titled “Sandbox”

Every verb is a WebAssembly component. A component has no ambient authority: it can call only the host interfaces it imports. No world offers sockets, and the filesystem interface is linked with no directories. At upload the host reads the component’s imports and rejects any outside the offered set with 403. See Capabilities and budgets.

Capability confinement

Section titled “Capability confinement”

Two invariants hold for every capability, in plain terms:

  • A verb never exceeds its caller. The object capability applies the same read and write rules as the HTTP data plane, evaluated for the caller, against the object’s owner. A verb bound to another user’s object can read and write only what the caller could through GET and PUT. The write check is shared code, so the data plane and the capability cannot drift.
  • A function is pure. Functions cannot write, publish or call actions, and the host refuses each at runtime. A GET therefore cannot change state, which is what makes the result safely cacheable.

Metering

Section titled “Metering”

Fuel, a wall-clock deadline and a memory cap bound every invocation, on both executor backends. Operators set ceilings that uploader-requested limits are clamped to, and per-tenant quotas on fuel, calls and storage. A composition tree draws on one shared budget, with bounded depth and fan-out and cycle detection. See Capabilities and budgets.

Run as the caller

Section titled “Run as the caller”

A verb executes with the caller’s authority, never more. Verbs that call verbs pass down at most the same authority. A verb can opt into running as its owner, but the execute check still runs against the real caller first, and cost still goes to the caller. Lifecycle hooks run as the principal who deployed them, so the user who triggers a hook does not lend it their authority. See Identity and authority.

Anonymous mutation

Section titled “Anonymous mutation”

Once any authentication is configured, anonymous callers can read and invoke public actions but cannot mutate. Deploys, management writes and data-plane writes return 401. With no authentication configured, the server is open by design and meant for loopback only.

Request admission

Section titled “Request admission”

Every request’s Host header must be a loopback name or listed in RESTACT_ALLOWED_HOSTS, which stops DNS-rebinding pages from reaching the server. /healthz and /readyz are exempt, so probes that address the container by IP work. A non-loopback bind without that list refuses to start. Browser-origin writes and every /mcp request from another origin are refused unless RESTACT_CORS_ALLOW_ORIGIN admits the origin. Global limits cap in-flight requests and concurrently executing verbs, and requests have a timeout that also covers the body transfer.

Authentication

Section titled “Authentication”

Identity comes from a verified OIDC token (RS256 or ES256, with the algorithm pinned from the signing key and a mandatory audience), an HS256 token, or a trusted header from a proxy. OIDC verification fails closed on any fetch or claim failure. All three OIDC variables (issuer, JWKS URL and audience) are required: setting only some of them, or any to an empty value, refuses boot and names what is missing. The JWKS URL must be https:// (plain http:// only to a loopback address), and the boot line auth: OIDC/JWKS verification enabled … confirms it. A set-but-unusable JWT secret or trusted-header setting refuses boot too, so a host never starts with auth silently off. The trusted header is unsigned, so it is safe only when the server is reachable solely through the proxy that sets it.

Process isolation

Section titled “Process isolation”

With RESTACT_ISOLATION=process, each request runs in a separate worker subprocess, so tenants do not share a process address space. The worker carries the full principal and applies the same limits, and the full conformance suite passes on both backends. The compile cache that workers share is sealed with an HMAC and checked before each load.

Egress mediation

Section titled “Egress mediation”

A verb has no network access. When the host makes an outbound call on a verb’s behalf, such as for the llm interface, the host does the work:

  • The destination must match an operator allowlist on the declared name. The host resolves it once, checks every resolved address against blocked ranges, and pins one, so DNS cannot rebind between check and use. Redirects are refused, and TLS verification is on.
  • The credential is stored as a secret, spliced in by the host at send time, and never visible to the verb. Secret values are zeroed on drop and never printed.
  • Request and response sizes, time and call counts are bounded and metered per principal.
  • A server configured with an egress allowlist but no secrets mount, or without a connector prefix, refuses to start.
  • Connector records must be governed so that only their owner can change them, both at call time and when they are created.

Secrets handling in logs

Section titled “Secrets handling in logs”

Caller-, guest- and deployer-chosen values are escaped before they reach a log line, so they cannot forge entries. Credentials embedded in operator-configured URLs are stripped before logging.

Storage

Section titled “Storage”

PostgreSQL connections require TLS by default. Weaker modes are refused unless you set the explicit plaintext opt-out, which is intended for loopback development. A durable data directory that cannot be opened stops the server rather than silently falling back to memory.

Trusted computing base

Section titled “Trusted computing base”

These components must be correct for the guarantees above to hold:

  • The host (restactd), including its HTTP layer, policy engine and executor.
  • Wasmtime, the WebAssembly runtime.
  • The two runner components, QuickJS and monty, which interpret all script verbs. Every script verb shares a runner, so a runner defect would affect all of them. They are built once and the host loads them from files you choose.
  • Native verbs registered by an embedding program, which run as trusted host code.

Operator responsibilities

Section titled “Operator responsibilities”

The server cannot enforce these for you:

  • Configure authentication before exposing the server beyond loopback.
  • Terminate TLS in front of the server and set RESTACT_ALLOWED_HOSTS to the names clients use.
  • Keep the trusted-header mode behind a proxy that sets the header and strips client copies, or use OIDC.
  • Decide who may deploy verbs, and seed collection roots before users arrive. Object ownership is first-writer-owns.
  • Set quotas and request ceilings that fit your load, and use a durable store.
  • Protect the secrets mount, the JWT secret and the compile cache key.
  • Run the production checklist in Production checklist.

Reporting a vulnerability

Section titled “Reporting a vulnerability”

Report a suspected vulnerability privately, using GitHub’s private vulnerability reporting on the restactd repository. Please do not open a public issue for a security problem.
