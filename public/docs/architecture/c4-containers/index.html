Containers

This diagram looks inside restactd. Its containers are the boxes typed [Container: …]. The others, including restact mcp and the conformance suite, are separate systems. A container here is a separately deployable or separately trusted unit, not necessarily a Docker container.

What you are looking at

Section titled “What you are looking at”
  • Host. The Rust server: HTTP routing, authentication, policy, the executor and the discovery document. Almost all logic is here. It embeds Wasmtime to run verbs.
  • Verbs. The uploaded components. They are untrusted code and run inside the host’s sandbox, one instance per invocation.
  • JavaScript and Python runners. Two trusted components, built once and loaded by the host. Script verbs are stored as source and interpreted by the matching runner inside the same sandbox.
  • Object and blob store. Where deployments, object data and binary values live. It can be in memory, on the filesystem, or in PostgreSQL.
  • restact mcp. The MCP bridge, a subcommand of the restact client that talks to the host over HTTP. It holds no state of its own and has no access to the host’s internals.
  • Conformance suite. A black-box test client that checks any compliant server against its discovery document.

The line between trusted and untrusted is the most important thing to read from this view. The host and the two runners are trusted. The verbs are not.

Relationships worth noting

Section titled “Relationships worth noting”

The host is the only container that touches the store. Verbs reach data only through the host’s capability interfaces, and script verbs reach it through a runner that goes through the same interfaces. restact mcp and the conformance suite see only what any HTTP client sees. For the guarantees this arrangement provides, read the Security model.
