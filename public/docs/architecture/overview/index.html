Architecture

This page maps the repository layout, the host’s modules, and the execution and capability model. Request lifecycle follows a request.

Repository layout (components)

Section titled “Repository layout (components)”

REST:ACT is a protocol and a Rust reference implementation. The repo is organized so the protocol artifacts (spec, contract, schema, conformance) are independent of the particular server that implements them.

PathComponentRole
spec/DecisionsMaintainer design notes. The protocol specification (the draft, concepts, registries) lives in stackumi/restact.
wit/ContractThe rest-act:plugin@0.1.0 WIT world — the host/guest interface every verb implements.
openapi/Description formatThe x-restact OpenAPI 3.1 extension for describing verbs (kind, binding, capabilities, call graph), plus a strict JSON Schema and a validator.
host/Reference serverThe Rust implementation: axum HTTP layer + Wasmtime executor. The management and invocation planes.
sdk/Guest SDKrestact-sdk (sdk/rust/), the Rust crate for writing verbs, plus guidance for other languages.
examples/Sample verbsword-count (function), summarize (action + composition), and the test verbs the black-box suites use.
conformance/Conformance suiteA black-box runner that drives any compliant server and is the executable definition of “compliant”.
site/Website + playgroundStatic site and an interactive verb playground, served same-origin by the host — opt-in (RESTACT_BUILTIN_SITE=1, off by default).
scripts/Dev/test scriptsBootstrap, builds, and the black-box test suites. See Development.

The host (host/src/)

Section titled “The host (host/src/)”

The reference server has two planes — a management plane (deploy and configure verbs) and an invocation plane (run them) — layered over a small set of pluggable subsystems.

Module reference

Section titled “Module reference”
ModuleResponsibility
lib.rsThe library crate root + axum HTTP layer: the run/run_default entry points (the embedding boundary — Embed restactd in a Rust app), run_worker, routing/dispatch (handle_v1), discovery, the :verb/{code,policy,meta,props} management plane, async operations, RFC 9457 error mapping, the static site + curated in-repo doc serving, verb bootstrap, the HostBuilder + register_route adapter, and the per-concern handler modules (discovery.rs, management.rs, invoke.rs, data_plane.rs, object_list.rs, registrations.rs). main.rs is a thin binary that calls restactd::cli::main(), which parses --help/--version and then calls restactd::run_default().
wasm_exec.rs + wasm_exec/WasmtimeExecutor. One execution path — every verb is a wasip2 component (bindgen! on the superset plugin-object-compose-event-llm WIT world). Owns fuel/epoch/memory limits, composition (shared budget, runs-as-caller), the gated object/event/identity capabilities, and data-property enforcement. Native (host-implemented) verbs are a DeployedVerb kind invoke_core dispatches to a Rust fn via wasm_exec/native.rs’s NativeCtx — the trusted analogue of the sandbox host state, reusing the same capability cores. The JavaScript/Python tiers register a shared QuickJS / monty runner component and interpret the stored source under the same limits/capabilities (no per-upload compilation).
registry.rsVerb resolution, keyed on (object-path-pattern, verb) with an ancestor walk. Binding = Entity ({id}) / Collection / Unbound. A DeployedVerb carries the component hash (or, for a script verb, the shared runner + a source_sha256; or a native handle), imports, allowed_calls, and the PropertyDef declarations. Native verbs are defaults registered by the embedder.
store.rsThe Store trait: MemStore (ephemeral) and the durable FsStore (content-addressed blobs/, deployments.json, per-object attribute state/ + an objects.json path index; @shared/<def-path> keys hold shared-scoped properties). The ordered query(prefix/order_by/predicate/cursor) primitive backs GET /v1 + the native query capability — a default scan on Mem/Fs, an indexed SQL query on PostgreSQL (pg/store.rs, feature postgres). Binary object values reuse the blob store via a $blob attribute reference.
policy.rsAuthorization via canonical subject matchers (public/owner/sub:/role:/group:/scope:/claim:). Verb policy actions (read/execute/write) are OR-lists of matchers, as are per-property ACLs and object $policy; public/owner are the defaults.
auth.rsThe ordered identity chain → Principal: trusted forwarded-identity header + HS256 JWT. Absent secret → anonymous-only.
oidc.rsGeneric OIDC/JWKS verification of a forwarded RS256/ES256 bearer JWT: alg pinned from the JWK, audience mandatory, iss/aud/exp/nbf/iat fail-closed; JWKS fetched over HTTPS behind an injectable seam (TTL-cached, throttled, run off-reactor). Consulted between the trusted header and HS256.
quota.rsPer-tenant fuel/call quotas, fail-closed — lifetime cumulative or windowed (RESTACT_QUOTA_WINDOW_SECS); names the tripped dimension + window rollover for the 429.
executors.rsThe Executor trait — the seam that lets the same verb run in-process or via process isolation.
process_exec.rsThe process-isolation backend: a worker subprocess carrying the full principal (RESTACT_ISOLATION=process).
sync.rsSmall synchronization helpers used across the planes.

Execution & capability model

Section titled “Execution & capability model”

Every verb runs as a sandboxed WebAssembly guest. There is no ambient authority: a verb can only reach capabilities its WIT world imports.

  • Substrate. Wasmtime (Cranelift), running WASI 0.2 Component Model components. Components are validated and content-addressed at upload; a cached InstancePre is reused per invocation under a pooling allocator.
  • The worlds (capability manifest). A verb targets plugin (host log only), plugin-compose (adds gated compose.invoke), plugin-object (adds gated object data access), or plugin-object-compose (both). The identity import comes with the object worlds; event and llm have their own worlds. The host binds the superset world. The world is the declaration: the host links a gated interface only for a verb that imports it, and Wasmtime wires only declared imports — so deny-by-default falls out for free. See wit/ and Authoring Verbs.
  • Native verbs & embedding. Beside uploaded components, a DeployedVerb may be backed by a host Rust function — a TCB verb the embedding application registers through HostBuilder, resolved/composed/run-as-caller exactly like any verb (it consumes no fuel; it’s trusted). This is how a platform exposes its own privileged primitives (an indexed cross-user query, a media transform) as composable verbs that untrusted uploads may call but not bypass. See Embed restactd in a Rust app.
  • Object-data capability. The object interface (get/set on the bound object’s declared data properties) is ACL- and scope-aware and attenuated like compose; the decision logic is the pure prop_read/prop_write_check. The bare-object data plane (GET/PUT /v1/<obj>) is the same data viewed as the object’s representation.
  • Resource limits (the triad). Epoch interruption (wall-clock → 408), fuel (deterministic CPU → 429), and a ResourceLimiter (memory → 507). These are normative regardless of which executor backend runs the verb.
  • Import allow-list. At upload the host inspects the component’s imports and refuses anything outside the world (e.g. a verb importing wasi:sockets is rejected 403 disallowed-import).
  • JavaScript tier (interpreted, not compiled). A text/javascript upload is stored as the verb’s source and interpreted at invoke time by one trusted, shared QuickJS runner component the host ships: the host frames the stored script + request input into the runner’s invoke(payload), and the runner bridges the host capabilities (log, compose, obj.get/set/getAt) to JS globals — so a JS verb has the same behaviors, gating, and limits as a wasm verb. There is no per-upload compilation (no compiler attack surface), and no second execution path: the runner is itself a component.

Composition

Section titled “Composition”

A plugin-compose verb may invoke another verb via compose.invoke (by route id, resolving up the tree). The host mediates every edge, deny-by-default:

  1. Declared call graph — every callable edge is declared at deploy time (?calls=a,b); undeclared edges are refused before execution and the graph is statically auditable.
  2. Authority attenuates, never escalates — the callee runs with a subset of the caller’s authority (consistent with runs-as-caller).
  3. One shared budget — the entire call tree debits a single resource pool (the primary denial-of-wallet defense).
  4. Bounds — max depth, max fan-out, and host-side cycle detection (a cycle → 508).
  5. Side-effect rule — functions chain freely; actions chain only when declared.
  6. Cross-server composition is just REST:ACT calling REST:ACT over HTTP — the protocol is recursive.

Identity: runs-as-caller

Section titled “Identity: runs-as-caller”

A verb runs with the caller’s principal. The invariant:

A verb’s effective authority = caller’s permissions ∩ the verb’s declared capabilities ∩ the target’s policy.

Cost is charged to the caller. A verb may opt into running with its owner’s subject-only authority instead (setuid-style, ?runs_as=owner) — the execute check still runs against the real caller, billing stays the caller’s, and it’s the deliberate exception for a privileged primitive a platform exposes.

Storage

Section titled “Storage”

The Store trait abstracts persistence. RESTACT_DATA_DIR selects the durable FsStore; without it the host uses the ephemeral MemStore.

  • blobs/ — content-addressed component/module bytes and original source (dedup by hash).
  • deployments.json — the verb registry (route id → binding, kind, code hash, policy, call graph).
  • page-token.key — the 32-byte key (mode 0600) that seals listing page tokens and verb query cursors. The server creates it at first boot; checkpoints do not copy it. On PostgreSQL it is the host_keys row page-token.
  • state/ — per-object attribute state written by verbs through the data-property ABI; @shared/<def-path> keys hold shared-scoped properties. An objects.json path index backs the ordered listing.

Two data-plane enablers sit on this store:

  • The query primitive (collections). Store::query — ordered (by a property value), prefix-scoped, predicate-filtered, keyset-paginated — backs GET /v1 object listing and the native query capability (ACL-filtered above the store, so listing ⊆ readable). A default scan on Mem/Fs; a real indexed SQL query with a (order, path) keyset on PostgreSQL.
  • Binary object values. A property whose value is binary (an avatar, post media) stores the bytes in the content-addressed blob store and keeps a small $blob reference in the attribute map — so the per-object size cap and whole-map rewrite apply only to the reference, not the media. Served back with the stored Content-Type + a content-hash ETag; read by verbs via get-bytes.

The active-active PostgreSQL backend (feature postgres, RESTACT_DATABASE_URL) is a third Store letting N stateless nodes share one database. Durability survives restart: an uploaded verb and its compiled module are re-loaded from the store (verified by scripts/persistence-test.sh).

Executor abstraction & portability

Section titled “Executor abstraction & portability”

The host does not hard-wire in-process Wasmtime. The Executor seam (executors.rs) lets the same component run in-process (wasm_exec.rs) or under per-request process isolation (process_exec.rs, RESTACT_ISOLATION=process), with identical observable behavior — proven by running the full conformance suite against both backends. A verb’s declared limits are normative regardless of backend.

Worker stdout is sacred. On the RESTACT_WORKER subprocess path, only the response goes to stdout; all diagnostics use stderr. See Development → Conventions.

Conformance & optionality

Section titled “Conformance & optionality”

The protocol is a small mandatory core + independently-advertised optional features. A host advertises what it supports in service.features of the discovery document; a client never assumes an unadvertised feature, and a verb may require a feature (the host returns 501 if it can’t satisfy it). The conformance suite gates each check on the discovery document — so the same suite validates a thin stateless gateway and a full transactional world server.
