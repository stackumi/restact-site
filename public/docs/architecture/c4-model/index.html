How the diagrams are made

The architecture diagrams are derived from the repository, not drawn by hand, so a diagram cannot show a module that no longer exists or miss one that does. The derived model is a Structurizr DSL file, docs/architecture/c4/workspace.dsl, which is committed. A check fails when the file no longer matches the source, so a change to the code that moves an arrow shows up as a diff in review.

What each part comes from

Section titled “What each part comes from”
Part of the modelDerived fromRule
System descriptionREADME.md, or docs-site/c4-descriptions.jsonThe system entry of the override file whenever it is present. Otherwise the whole sentences of the first prose paragraph that fit in 160 characters, with the title and badges skipped and markdown removed.
PeopleFixed, plus cli/src/mcpA client and a verb author always; an AI agent when the restact mcp bridge module exists.
ContainersDirectoriesThe host, the verbs and the object store always; the JavaScript runner when examples/js-runner exists and the Python runner when examples/py-runner exists. The host’s technology line carries the Wasmtime version from host/Cargo.toml.
External systemsFilesAn external system appears only when its source does: the identity provider needs host/src/oidc.rs, PostgreSQL needs host/src/pg, outbound origins need host/src/egress.rs, telemetry needs host/src/telemetry, the secrets backend needs docker-compose.openbao.yml, and the conformance suite needs conformance/Cargo.toml.
Host componentshost/srcOne component per .rs file or subdirectory. Test files, modules the crate root declares under #[cfg(test)], and the tests and bin directories are left out.
Component descriptionThe module’s leading //! commentThe first sentence of the first paragraph, with markdown and references to internal documents removed, cut at 120 characters with a trailing …. A module whose comment cannot be made to read well on its own gets an entry in docs-site/c4-descriptions.json.
Groupsdocs/architecture/subsystems/*.mdEach subsystem note lists the files of one concern under sources: in its frontmatter. A module belongs to the first group, in a fixed priority order, that lists its file or a path inside its directory. Modules in none go to Support. Every listed path must exist, or the generator fails and names the note and the path.
Arrows between componentsThe crate sourceA lexical scan counts the references from each module to each other module: the names a use brings in, qualified paths such as store::Store::new, and later uses of an imported name. Comments, strings and #[cfg(test)] items are not counted, and method calls are not seen. An arrow exists when a non-test use links two modules, or when the references between them reach the minimum weight. The crate root lib.rs is the component lib. Every arrow is labelled uses.
Which arrows show--min-weight (default 35)A host arrow whose ordered pair of modules has fewer references than that is minor. The HostComponents overview hides minor arrows. A group view shows its members and the neighbours joined to a member by a non-minor arrow. Arrows in the client core and the bridge are never minor.
Split viewsMember countA group of more than 12 members becomes numbered views (HostSupport1, HostSupport2, …) over the module names in sorted order.
restact mcp componentscli/src/mcpThe same module rule as the host, without groups. One scan of cli/src serves the bridge and the client core.
Client core componentscli/srcThe same module rule as the host, without groups, when cli/Cargo.toml exists. The crate root lib and the testing support module are left out. The bridge builds on the core (a library) and reaches its host module; the core has no edge to the host, because the bridge process makes the HTTP calls.
DeploymentDockerfile, docker-compose.postgres.yml, docker-compose.openbao.ymlOne node per service in the compose files and one for the image.

Colours

Section titled “Colours”

The diagram colours are not set in the generator. It reads the --c4-* colour tokens from the site’s stylesheet, docs-site/src/styles/theme.css, and exits with an error naming any token that is missing. Only the element in scope carries the accent outline: the restactd system in the context view, and the host container in the container, deployment and host component views. The restact mcp and client core component views have none. The site build removes the accent from the enclosing restactd boundary so that each view has one lit element. Other elements use the neutral element, person and external colours. Relationship lines use the edge colour; the plate, soft ink and edge-label tokens are carried by the page styles and the Mermaid theme, which the DSL cannot set.

From DSL to page

Section titled “From DSL to page”
  1. make c4-gen scans the source and writes docs/architecture/c4/workspace.dsl. Commit the result.
  2. make check-c4 regenerates the model in memory and fails if it differs from the committed file. The message names the first line that differs. It reads only the repository, so it needs no Docker and no prebuilt data.
  3. Structurizr validates the file and exports each view to Mermaid with export -format mermaid, run from a Docker image pinned by digest. The exports land under docs-site/build/c4/ and are not committed.
  4. The site build replaces each <!-- c4:ViewKey --> line in the architecture pages with the matching diagram. A marker ending in *, such as <!-- c4:HostSupport* -->, embeds every numbered view of that name. In the container view it also removes the restactd boundary box, because Mermaid cannot lay the external systems out cleanly around it.
  5. The Mermaid renders to SVG at build time.

If a required source is missing, the generator exits with an error that names the path. If a subsystem note lists a file that does not exist, it names the note and the path. Output is sorted and has no timestamps, so two runs on the same tree are byte-identical, and a fresh checkout reproduces the committed file.

Build the site locally

Section titled “Build the site locally”

You need the tools in mise.toml (mise install gives Node 24 and pnpm) and Docker for real diagrams. make docs-site-install installs the site’s dependencies and also downloads the headless Chromium that draws the diagrams; it draws them even when C4_EXPORT=skip replaces the C4 views with placeholders.

The dev server listens on http://127.0.0.1:9191/restactd/. It serves the copy of the pages under docs-site/src/content/docs/, so an edit under docs/ shows up only after you run make docs-site-sync again. C4_EXPORT=skip lets you edit pages without Docker. The generator and the site checks have their own tests in docs-site/scripts/.

Changing what the diagrams show

Section titled “Changing what the diagrams show”

To change a group, edit the subsystem note that lists the files. When code moves, update the sources: of the note that names it, because a missing path fails the generator. To change an arrow, change the code: the diagram reports the references that exist, and a pair drawn as minor becomes visible in the overview once it reaches 35. To change a description, edit the module’s doc comment, or add an entry to docs-site/c4-descriptions.json. To change a colour, edit the --c4-* tokens. Then run make c4-gen and commit the DSL with the change. Do not edit the generated file by hand.
