HTTP API

The wire surface of the reference host. This is a practical reference; the normative definitions are in the REST:ACT specification, which also covers the conceptual model.

The data and verb API is under /v1. The host also serves /healthz, /readyz, the discovery document, /openapi.json and /operations at the root, /mcp when RESTACT_MCP=1, and the operator routes under /admin when their variables are set, plus — opt-in via RESTACT_BUILTIN_SITE=1 — the static site and curated in-repo documentation.

curl + {id} patterns. When a route contains literal braces (bound-verb patterns), pass -g (globoff) or URL-encode them as %7Bid%7D, or curl mangles the path.

Data plane (the noun)

Section titled “Data plane (the noun)”

Besides verbs, an object has data — its representation. With the data-plane feature, a bare object path (no :verb) is that representation:

GET returns the properties the caller may read; PUT merges its members, each stored typed (feature typed-values: a string, number, boolean, array or object, returned as sent), and a top-level null member removes that property (feature put-null-removes; a null for an unset property changes nothing, "$policy": null removes the object’s own policy (below), for $owner or any other $ attribute it is 400, and for a set final property 409 property-final). Numbers follow I-JSON: finite, and a whole-number value within ±(2^53−1), so 1e21 is 400 invalid-input (an integral double folds to an integer and -0 to 0; send a larger value as a string). Nesting deeper than 64 levels is 400. $ members keep their shapes: $policy may be a JSON object (stored and served as a JSON string via ?meta=policy), a non-string $owner or any other $ member is 400. The ETag is over the RFC 8785 canonical form of the readable map, so it is unchanged for an all-string object (a non-empty body needs a Content-Type: application/json or a +json type for a merge, else the value’s own media type), honoring per-property write ACL and final. A string or member name holding U+0000 (in a value or as a property name) is 400 invalid-input, on every store, and nothing is written. GET of an object with no stored data is 404. On a path no :update accessor serves, a PUT with a non-empty body and no usable Content-Type (none, a blank media type, or one that is not a single type/subtype, or has a comma anywhere in it) is 415 invalid-input and writes nothing; more than one Content-Type line is refused the same way whatever the body. An accessor receives the body unparsed. DELETE removes the object (204). A caller who may not read an existing object gets the answer an absent one gets: 404 from DELETE, and from PUT the answer the same PUT gets at an absent path (the creation rules’ 403 or 404 where they refuse it, else 404, and nothing is written); a caller who may read it but not change it gets 403. POST and PATCH go to an accessor verb (:create, or :set then :update) and answer 405 without one. This is the data that object-capable verbs read and write via the object interface.

Boundaries:

  • First-writer-owns; undeclared properties are public-read. The first writer of an object becomes its owner ($owner); an undeclared property is then writable only by that owner (transparent under the anonymous-open default, where everyone is anonymous) and readable by anyone. Declare a property with an acl/final to restrict reads or open writes. Do not expose a host beyond localhost without auth (see Configuration → Security).
  • Object policy + ownership. Two $-prefixed fields are client-writable through the data plane (every other $- or @-prefixed member is in a reserved namespace — 400, nothing stored, and that includes a null member):
    • $policy — a {read, write, delete} baseline policy (canonical matchers), gated by the object’s current write policy. Read it back with GET /v1/<obj>?meta=policy (the effective policy + $owner, gated on manage authority — i.e. the object’s write policy; a denied/missing object is 404), or ?meta=policy&raw=1 for only the dimensions explicitly set (unset stay empty). "$policy": null (feature put-null-removes) removes the object’s own policy, so it falls back to its governing anchor’s policy or the defaults. It needs the authority a $policy rewrite needs, and is refused on a secrets-mount slot (422 invalid-input), under the connector prefix (422 connector-birth-ungoverned), and with RESTACT_GOVERNED_CREATION=1 at a path no anchor governs (403).
    • GET /v1/<obj>?meta=provenance (feature object-provenance) returns {created, updated}, each {subject, actor?, at} — who created and last wrote the object (every committed mutation, $policy/$owner and blob writes included), actor only for a write made under delegation, never a grant id; at is RFC 3339 UTC to the second. It is read-gated by the object’s own read (a denied or missing object answers as a GET does, 404), never part of the representation.
    • $owner — ownership is fixed: no write changes it. PUT /v1/<obj> {"$owner":"<subject>"} is admitted only from the object’s current owner and only when the value equals that owner (after the usual trim), which is a no-op, so a GET-then-PUT keeps working. Any other value, or any other caller, is 403 and the write changes nothing; an empty or non-string $owner is 400. There is no transfer: grant access with $policy instead (sharing lends access without moving the owner), and copy an object to give someone their own. An operator can recover ownership with POST /admin/reown. A creating write by an authenticated caller that carries $owner stays 403, because an absent object’s effective owner is anonymous. An object a verb creates with a bound object.set records the frame principal as its owner, and no write records an owner on an existing ownerless object. An ownerless object’s $policy and $owner writes are gated as if anonymous owned it (a named caller is refused unless the object’s write policy admits the caller); data-member writes to it claim nothing. A governing anchor’s write policy must admit the caller, and its owner matcher means the anchor’s $owner. With no governing anchor the write is admitted, except under RESTACT_GOVERNED_CREATION=1, which refuses it with 403. The bound object.set and the foreign set-at follow the same rule.
  • shared-scoped properties are not writable here (403) — they’re single-valued on the definition object; write them through a verb’s object.set. They’re also excluded from GET (they aren’t part of a concrete object’s representation).
  • The reserved @ namespace is not addressable (400): @shared/<def> storage keys can’t be read or written through the data plane or get-at, and no verb can be deployed or invoked under an @ segment. A property name beginning @ is reserved like one beginning $: a PUT member, a secrets-mount PUT member, a verb write and a declaration with such a name are refused, and reads never return one.
  • A . or .. path segment is not addressable (400 invalid-input), whether sent literally or percent-encoded (%2e, %2E). This applies to every data-plane method including OPTIONS and PATCH, to :verb invocation, and to the prefix of GET /v1; the refusal comes before any 404 or 405 and does not echo the path. The :verb/<property> management routes and verb deploy refuse such a path (and an @ segment) the same way. A verb’s own object calls refuse such a path as they refuse an @ segment, and a compose target with one answers not-found; a schedule or subscription target with one is 400 invalid-input. An object path a verb names is never percent-decoded, so %2e%2e there is an ordinary name. Other names with dots (a.b, ..., .hidden, x..y) are valid.
  • Per-object caps: at most 1024 properties and 1 MiB of data per object (413 beyond), and data-plane writes are metered against the per-tenant quota (RESTACT_QUOTA_CALLS).

Binary object values

Section titled “Binary object values”

An object’s value can be binary — an avatar, post media — not just JSON properties (features binary-values + object-binary). A bare-object PUT with a non-JSON Content-Type stores the body in the content-addressed blob store; the object’s representation then is those bytes:

  • A GET of a binary object always serves the bytes (with the stored Content-Type, a content-hash ETag so If-None-Match → 304, and nosniff) — there is no JSON view of it. The response is privately cacheable: Cache-Control: private, max-age=3600 + Vary: Authorization (blob reads are ACL-gated per principal, so only a browser cache may hold them, keyed on the bearer token; the content-hash ETag makes staleness harmless and the 304 refreshes both headers). Internally the bytes live in the dedup’d blob store and the object keeps a tiny $blob/$blob-type/$blob-size reference, so the per-object size cap bounds the reference, not the media.
  • Active content is neutralized. Because the bytes and the Content-Type are caller-controlled and served on the host’s own origin (default policy is public-read; the site + API are same-origin), a served blob carries the same restrictive Content-Security-Policy as a verb’s HTML output, and a script-capable type (text/html, image/svg+xml, any *+xml) is additionally served Content-Disposition: attachment — i.e. it downloads instead of rendering inline, so a stored HTML/SVG object value can’t run script same-origin. Images (image/png, …) still display inline. Conversely, a Content-Type in the JSON family (application/json or any +json suffix, e.g. application/activity+json) is not binary — it is stored as a queryable JSON noun (property merge), not a blob.
  • The blob is size-capped by RESTACT_MAX_BLOB_BYTES (default 8 MiB → 413), and a blob PUT is metered (bytes-written) against the per-tenant quota.
  • Verbs read these bytes via the object capability’s get-bytes (wasm/native, and obj.getBytes() / obj.get_bytes() in the JS and Python tiers, up to a quarter of the script heap) — the read-time media-transform pattern. Verb-persisted binary (set-bytes) is not available.

Object collection (GET /v1) and queries

Section titled “Object collection (GET /v1) and queries”

GET /v1 lists the client-addressable objects with stored data the caller may read — the object collection (feature object-listing). Listing is always ⊆ what the caller could read (ACL-filtered), ordered by path in byte (code-point) order, and paginated:

nextPageToken is an opaque, sealed token the server issued for this listing and caller. It is bound to the filter and the caller, so pass it back unchanged on the same request shape. A pageToken the server did not issue for that listing and caller (built by hand, altered, from another filter or another subject) answers 400 invalid-input. An empty pageToken means the first page. pageSize may change between pages.

prefix (feature object-listing-prefix) keeps only the objects whose path starts with the given string. It is empty or ends in /, so ws/7/ lists everything below ws/7 at any depth and not ws/7 itself, which you read with GET /v1/ws/7. The value is form-decoded, so send a literal + as %2B. Two cases answer 400 invalid-input: a prefix that does not end in / (ws/7), and one no listable path can begin with (a leading /, an empty segment such as a//, a . or .. segment, a segment that starts with @, or a NUL). The nextPageToken is bound to its prefix, so repeat the same prefix on every page; a different prefix, or none, is the same 400. Send prefix only when discovery advertises object-listing-prefix: a host without the token may ignore it and return the whole listing. On PostgreSQL the prefix is a byte range over the object_attrs_path_pattern (text_pattern_ops) index, and path order is byte order, the same as on the in-memory and file stores.

The filter=/read_mask= refinement is the object-query feature (a filter that is not key=value is 400 invalid-filter); GET /v1 itself orders by path. The richer ordered query primitive (order by an arbitrary property, descending, keyset cursor) is reached from verbs through the object capability’s query (feature verb-object-query), or by composing a native query verb the platform exposes (e.g. feed:candidates), so a timeline/outbox/search is one indexed query rather than a scan. On the PostgreSQL backend both the listing and that primitive are indexed SQL. See Embed restactd in a Rust app → the query primitive.

Event streams (SSE)

Section titled “Event streams (SSE)”

With eventing enabled (the event-subscriptions feature), a bare-object GET content- negotiated with Accept: text/event-stream returns a long-lived Server-Sent Events stream of the object’s events instead of its representation:

  • Read-gated like a data-plane GET: a caller who could not read the object receives no stream.
  • Replay + resume: each event carries a monotonic id; reconnect with Last-Event-ID: <id> (or ?after=<id>) to replay only events after it. A subscriber that falls behind receives a gap event whose data is {"$publisher":{"kind":"host"},"missed":<n>}, signalling it should reconnect. A resume whose Last-Event-ID is older than the oldest retained event of the topic (evicted by the event-count, per-topic byte or across-topic byte bound, or trimmed from the PostgreSQL log) starts with the same gap, missed counting the evicted events after the cursor (an upper bound when many have been evicted or when the topic was dropped and recreated meanwhile). On PostgreSQL missed is absent when a replay query failed and the count is unknown, and a clean reset also gives a stale cursor a gap. A gap frame carries no id: line, so it never moves the client’s Last-Event-ID. A fresh subscribe gets none, and a host that has restarted without the durable log has no memory of what it dropped, so it sends none either.
  • Publisher stamp: every frame’s data is a JSON object carrying a $publisher member. It is {"kind":"host"} for an event the server publishes (data-plane lifecycle events, checkpoint events) and {"kind":"verb","verb":"<deployed route pattern>"} for one a verb published, such as widget/{id}:notify, never the concrete route.
  • Bounded: concurrent streams are capped (RESTACT_MAX_SSE_STREAMS, 503 past the cap) and each stream ends after RESTACT_SSE_MAX_SECS so the client reconnects with Last-Event-ID.
  • Kill-switch: with RESTACT_DISABLE_EVENTS set, the discovery token is omitted and this same request falls through to the normal data-plane representation (the complete kill-switch).

A verb publishes to its object’s stream via the gated event capability (event.publish); the host also auto-publishes data-plane changes. An event name is 1-128 bytes with no ASCII control characters (U+0000-U+001F, U+007F); anything else is refused invalid-input at publish (a verb surfaces it as 422). onCreate, onChange, onDelete and gap are the server’s own names: a verb publishing one gets 403 forbidden. The data is empty or one JSON object with no top-level member whose name starts with $ (else invalid-input); the host adds the $publisher member and leaves the rest of the text as the verb wrote it. The topic is at most 1024 bytes (else invalid-input, 422 from a verb); the stored data, stamp included, is at most RESTACT_EVENT_MAX_DATA_BYTES, and one invocation publishes at most RESTACT_EVENT_RING_MAX_BYTES in total, over either being 413 object-too-large with nothing stored or broadcast. A verb that publishes to a topic others read thereby discloses its deployed route to them. See Configuration → Eventing.

Management plane

Section titled “Management plane”

Deploy a verb

Section titled “Deploy a verb”

description is deployer-authored prose, for people and models — documentation, not a declaration of behavior; no effect on invocation, authorization, or any other property. UTF-8, ≤ 1024 bytes after decoding; over the bound is 400 invalid-input, never truncated. (The verb route is likewise bounded: 1024 decoded bytes by default, RESTACT_MAX_ROUTE_BYTES; over it is 400 invalid-input, route exceeds N bytes (got M).) Absent or empty → none declared. Reflected verbatim (never redacted) in discovery, :verb/meta, /openapi.json’s x-restact-verb, and the /mcp facet’s list_verbs. A POST replacement re-declares it (an omitted value clears a previously-declared one); PUT :verb/code and a rollback preserve the currently-registered one. The KEY is matched literally — a percent-encoded spelling of the key itself (e.g. %64escription=…) is not recognized as description and is silently ignored as an unrelated query parameter; only the value is percent-decoded.

input_schema and output_schema (feature verb-schemas, always advertised) declare the verb’s input and output as JSON Schema 2020-12, each the percent-encoded JSON text of one schema, at most 8192 bytes after decoding. They are documentation for clients and models: the host never validates an invocation against them. A schema must be self-contained: a JSON object or a boolean, $schema only at the root and only the 2020-12 URI, no $id, $anchor, $dynamicAnchor, $dynamicRef or $vocabulary, every $ref a #/... JSON Pointer that resolves to a subschema inside the document (use $defs; legacy definitions is refused), at most 64 levels deep, no U+0000, and every standard keyword of the right shape. A violation is 400 invalid-input naming the parameter and the pointer of the node, and nothing is deployed. They are emitted unredacted as inputSchema and outputSchema in discovery, :verb/meta and x-restact-verb, and re-declared by every POST (omitting one clears it); PUT :verb/code and a rollback preserve the registered ones. A host without the token ignores the parameters, so clients check service.features first.

fuel is the verb’s per-invocation compute, clamped to the operator ceiling. A JavaScript or Python verb is parsed on every call out of that fuel, so a large source (roughly 73 KB of Python or 185 KB of JavaScript, depending on the source) can exhaust the default and answer 429 unless it is deployed with a higher fuel.

produces declares the verb’s output media type (e.g. text/html), which the invocation response carries; absent → application/octet-stream. object=deny / compose=deny / event=deny / llm=deny each withhold their gated capability if the component declares it (a grant can only withhold, never add) — event is the event-publish capability; llm is the typed-connector capability. Deploy refuses a function-kind wasm-component verb that declares llm at all. A source-language verb is never refused at deploy time; its effective llm grant is withheld instead. Either way llm=deny has no effect on a function, since it never has the grant deny would withhold.

Caution

produces: text/html is attacker-controlled output. A verb that renders object data to HTML is emitting bytes derived from possibly-malicious uploaded data. The host hardens such responses with X-Content-Type-Options: nosniff and a strict Content-Security-Policy, but the verb must still escape raw HTML and allow-list URL schemes (reject javascript:/data: in links/images) — see render-html for the reference. Don’t serve such output same-origin with privileged cookies.

The host validates the upload, checks the import allow-list (rejecting disallowed imports with 403 disallowed-import), content-addresses and persists it, and registers the route. Returns 201 Created with a Location of /v1/<verb> and a body of verb, kind, sha256 and imports.

Born private (feature verb-private-default). A new verb’s policy admits only its owner (the deployer) for read, execute and write: other principals see it in discovery but cannot invoke it or read its properties until the owner shares it with PUT …/policy. exec is the one-step shorthand for execute only: exec=public lets anyone invoke it (its read stays owner), and exec=owner keeps it owner-only. Any other exec value, empty included, is 400 invalid-input. On an anonymous-open host (no auth configured) every caller is the owning anonymous principal, so the born policy makes no observable difference there; strict exec and the keep-the-policy replacement rule below apply there too. Without the feature, a new verb is born read/execute = public, write = owner.

Replacing a verb. A POST at a route that already holds a registration replaces it. A replacement by the owner keeps the existing policy; exec, when given, overrides execute and nothing else. To change any other part of the policy, use PUT …/policy. A replacement by a non-owner holding write keeps the policy verbatim and refuses exec (400).

Create-only (feature verb-conditional-requests). Send If-None-Match: * to create the verb only if the route is free: when a registration already exists at that exact route (the reference host refuses an object path with an empty segment, 400, and treats any {name} wildcard as {id}, exactly as for replacement), the host answers 412 precondition-failed and changes nothing, or the replacement’s 401/403 if you could not have replaced that verb. Of concurrent create-only requests for one route, handled by one host process, at most one succeeds (the serialization is per node; see the paragraph on conditional management writes below). It is the only precondition this endpoint accepts: any other If-None-Match value, or an If-Match, is 400.

Discovering the endpoint (feature verb-reference-deployment). A host that advertises it accepts POST /v1/modules as described here. A host without the token may still accept it, so a client may try; if the host refuses it as unsupported (404, 405 or 501), it does not accept verb deployment this way; do not retry.

Source languages. The ?lang= query parameter declares a source language; the Content-Type header alone does not. Without ?lang=, the body is treated as a WebAssembly component, and a script sent that way is refused 400 (invalid-component). With the optional source-languages feature the host accepts lang=text/javascript: the script is stored as the verb’s source and interpreted server-side by the shared QuickJS runner (no client compile, no per-upload compilation). The upload is syntax-checked at deploy by a compile-only parse; a script that does not parse is rejected 422 (restact_code: invalid-source), carrying the engine’s message — instead of a 201 that only fails at first invoke. A check that outruns the operator’s window (RESTACT_SOURCE_VALIDATE_WALL_MS) is not a verdict on the script: it is 503 unavailable with Retry-After, and nothing is stored. Runtime faults still surface at invoke (script-error). A ?lang= value with no registered runtime returns 415 (unsupported-language).

Verb properties

Section titled “Verb properties”

A verb is an object; its facets are addressed as properties and operated on with ordinary HTTP methods. The conventional (RECOMMENDED, not required) names are below.

PUT …/code and PUT …/policy can create a registration at the request’s concrete route, so a route over RESTACT_MAX_ROUTE_BYTES (default 1024 bytes, counting the longer of the decoded route and its stored {id} form) is 400 invalid-input there too; reads, DELETE, PUT …/props and rollback are not length-checked.

PropertyGETPUTDELETENotes
…/coderead effective code (Accept negotiates source vs. wasm); ETag = sha256 of the source (or the component)upload/replace (Content-Type = language)removewrong type → 415; oversized → 413
…/policyread the authorization policy (with its own ETag†)set the actions you send (omitted actions keep their value; fail-closed validation → 400); owner-only (manage); the owner member can only restate the current owner—{owner, read, execute, write}; each action is one matcher or an OR-list
…/meta{route, verb}: the verb descriptor (kind, binding, limits, declared capabilities, call graph); the owner is in …/policy——read-only
…/propsdeclared data properties (with its own ETag†)replace the declarations (a name beginning $ or @ is reserved → 400)—the data-property profile

Each policy action (read/execute/write) is an OR-list of canonical subject matchers — public, owner, sub:<id>, role:<r>, group:<g>, scope:<s>, claim:<k>=<v> (the same vocabulary as per-property ACLs and object $policy), plus, in verb policy only, readers:<path> (feature readers-matchers): it admits whoever may currently read the object at <path>, checked on every request, so sharing or unsharing that object shares or unshares the verb. An absent or unreadable object admits no one; readers: in object $policy or a property ACL is 400. Careful: an object with no $policy of its own and no governing anchor is publicly readable by default, so readers: pointing at it admits every caller, anonymous included. Point readers: at an object with its own $policy or under a governing anchor. A single matcher may be written as a bare string and reads back as one; a list reads back as an array. A verb created through POST /v1/modules starts owner-only for every action (feature verb-private-default); exec=public opens execute. An action omitted from a PUT …/policy keeps its current value, so {"execute":"owner"} narrows execute and leaves read and write alone. An unrecognized matcher or an empty list → 400.

A verb’s owner is fixed. The owner member of a PUT …/policy body is read like this:

owner memberResult
absentthe owner is kept
a string exactly equal to the current owner (no trimming, no case folding)no-op; the rest of the body applies
a string that differs403 forbidden; nothing in the body is applied
present but not a string400 invalid-input

Re-registration, PUT …/code, PUT …/props and rollback keep the owner too. An operator can recover ownership with POST /admin/reown.

History and rollback (feature verb-history). GET …:verb/history returns the verb’s current hash triple, owner and timestamps plus a bounded, newest-first list of superseded deployments (never the code bytes); it needs write on the verb. POST …:verb/rollback, naming a history entry by its full hash triple, rebinds the verb’s code to that version and changes nothing else (owner and policy are kept). It is gated like PUT …/code.

† Conditional management (feature verb-conditional-requests). code, policy and props each carry their own ETag, and a policy change never invalidates a code tag (or the reverse). If-Match is honoured on PUT/DELETE …/code, PUT …/policy, PUT …/props and POST …/rollback (compared with the current code tag: use the ETag of the default, source representation of GET …/code, not of an Accept: application/wasm read); a stale tag is 412 precondition-failed and nothing changes. Successful PUTs return the new tag. Preconditions are checked only after authorization: a caller without the right gets its 401/403, never a 412. Within one host process, the reference host runs every write to a verb, and every POST /v1/modules to the same exact path pattern and verb name (a write to an instance path of a wildcard verb is keyed on that instance path), in one serialized step, so two conditional writers to one facet cannot both succeed and a policy write is never lost to a concurrent re-upload. That serialization is per node: on a multi-node PostgreSQL deployment it does not span nodes. An If-Match or If-None-Match value that is not visible ASCII is 400, never ignored. Without the token, only PUT …/code honours If-Match.

Writing follows the prototype model: PUT /docs/42:noise/code defines noise on that entity (an override); GET returns the effective code, resolving up the chain.

Which properties exist, and which methods each accepts, is host-defined and discoverable — clients learn it from OPTIONS (the Allow header) and the discovery manifest, never by guessing.

Discovery

Section titled “Discovery”

Clients never assume a feature; they ask.

The discovery document advertises the service version, consistency level, the optional features the host supports, defaultCapabilities, and the verbs with their kinds, limits, declared capabilities, and call graph. It lists only the verbs the caller may read, invoke or manage, so two callers can see different lists; a credential that fails is refused 401, and no credential is the anonymous caller. Each response carries Vary over the identity headers the host reads, and one computed for a signed-in caller is Cache-Control: private, no-cache.

service.acceptedSourceLanguages lists the upload Content-Types the host accepts — always ["application/wasm"], plus each source language with a registered runtime (e.g. "text/javascript"). When a non-wasm language is available the host also advertises the source-languages feature token. A host started without the JS runner advertises neither, and an upload with ?lang=text/javascript returns 415.

service.openapi (always /openapi.json on the reference host, feature token openapi-document) points at a generated OpenAPI 3.1 description of the server’s live surface — every verb route the caller may read or invoke as a path (the same filter as discovery), x-restact carried through. GET /openapi.json serves it unconditionally. A verb that declares inputSchema/outputSchema has each emitted once under components.schemas (named from a hash of the route, so bounded by the schema size, not the route length) and referenced as {"$ref": "#/components/schemas/<name>"} from the request body, the 200 response and, for a function, a ?input= query parameter; a verb that declares none is unchanged. A client (or the MCP bridge, cli/src/mcp/) can use it to enrich tool/request schemas instead of guessing from the discovery document alone.

An operator MAY additionally set RESTACT_OPENAPI_SPEC=<path> to an OpenAPI 3.1 base document: the host then MERGES it with the same generated parts on every request instead of serving the bare generated document. info."x-restact" and each verb’s x-restact-verb always stay live (a stale operator claim can never survive a merge); a path/method the base already documents keeps the operator’s own operation object, refreshing only its descriptor; everything else in the base — notably the bare-object data plane, which the generator has no way to document on its own — passes through untouched. The host performs no automated data-plane generation or inference: the base is the only source of that documentation. openapi/examples/library.openapi.yaml is a worked example (the book-API demo’s data plane).

Presentation verbs (feature token presentation-verbs, always advertised): a kind=function verb deployed with ?produces=application/vnd.restact.ui+json returns a declarative UI document — a JSON tree of components from a fixed catalog (the trust boundary) that a catalog-aware client renders. Such a verb carries role: "view" in its descriptor (unless its name is a reserved accessor/lifecycle name, where the produces type is the equivalent signal), so a client builds its navigation from discovery: untemplated views (library:homeView) are top-level, templated ones (library/book/{id}:detailView) are per-object. See the presentation verbs in the REST:ACT specification.

Cross-cutting semantics

Section titled “Cross-cutting semantics”

A route that resolves to no verb definition answers 404 with restact_code verb-not-deployed and the fixed detail no verb deployed, for every method and every caller. Resolution reads only the deployed definitions (the ones discovery lists), never the object’s stored data or who may read it, so the answer says nothing about which objects exist. Other checks keep their place: a . or .. segment is 400, a bad credential is 401/403, and a wrong method on a deployed verb is 405. A route with an empty segment, and a bare path that names no verb, are plain 404 not-found. A route with an @ segment is refused 400 invalid-input at the edge, before resolution (the @ namespace is reserved). The host advertises the feature verb-not-deployed in service.features.

A verb that ran never produces the code for its caller. When a verb returns verb-not-deployed, or passes it up from a call it made, the caller of that verb gets 404 not-found with the same message. A composing verb can therefore read verb-not-deployed, and only that, as “nothing is deployed there”. See Composition.

A request whose Host is not localhost, 127.0.0.1, [::1] or listed in RESTACT_ALLOWED_HOSTS gets 403 forbidden (/healthz and /readyz are exempt); a duplicate, non-text or malformed Host gets 400 invalid-input. A request that is not GET/HEAD/OPTIONS, or any request to /mcp, is refused with 403 forbidden when a browser marks it cross-origin (Sec-Fetch-Site, else Origin against the request’s authority) and its origin is not listed in RESTACT_CORS_ALLOW_ORIGIN. Clients that send neither header (curl, SDKs, the bridge) are unaffected. The detail names the variable to set and never echoes the value.

A URL path containing %00 (a decoded U+0000) is 400 invalid-input on every route and method, reads and deletes included, before authentication; the query string is not checked, because verb input travels there. The upload parameters of POST /v1/modules (verb, description, calls, the schemas) may not contain %00 either.

A JSON request body the host parses must not repeat a member name in any object, at any depth. Such a body is refused 400 invalid-input, naming the member, after authentication and before any authorization or lookup, so every authenticated caller gets the same answer. An anonymous mutation on a host with auth configured is 401 first, without the body being parsed; with no auth configured the check runs first. This covers data-plane PUT bodies sent as JSON (a non-JSON body is stored as a blob, and an accessor-mediated data-plane PUT is checked the same way), verb policy, props and rollback bodies, sub-token mint, grants (create and patch; redeem is unauthenticated and answers 400 to everyone), schedules, subscriptions, /admin/reown and the JSON-RPC body of POST /mcp (a 400 with a JSON-RPC parse error). A disabled schedule or subscription surface still answers 501. A string or member name holding U+0000 in those same bodies is refused 400 invalid-input the same way, before any lookup (the detail never echoes the value); a $policy matcher or a secrets-mount value holding it is refused too. Verb input is not parsed by the host and is not covered, which includes the POST and PATCH bodies an accessor verb receives.

Conditional requests

Section titled “Conditional requests”

ETag + If-None-Match / If-Match (RFC 7232) for caching and optimistic concurrency:

A failed If-Match precondition returns 412. On the object data plane (GET and PUT /v1/<obj>) both headers go through one parser: repeated header lines combine as one comma list, * cannot be mixed with entity-tags, and a value that is not a quoted entity-tag or contains bytes outside visible ASCII is 400 invalid-input. If-Match compares strongly (a W/ validator never matches) and If-None-Match compares weakly.

Preconditions apply only where the response without them would be a success or a 412 (RFC 9110 section 13.2.1). On a GET, a well-formed If-Match that does not match the current ETag of a readable object is 412, and a matching If-None-Match (including * on an existing object) is 304. An object that is absent or not readable by the caller is the plain 404 whatever the headers say, and a malformed header is 400 only for a caller who may read the object. If-Match is evaluated first.

On a PUT the same rule applies to JSON values, binary values and the secrets mount, evaluated inside the write lock after the write-authority check (RFC 9110 section 13.2.1). A caller who may read an object but not write it gets 403, never a 412 that shows whether its state matched, and never a 400 for a malformed header or for a precondition the secrets mount does not support. A caller who may not read an existing object is answered as the same request is at an absent path, where a write that would create is still refused the same way: the precondition’s outcome (412 for an If-Match that nothing can satisfy, 400 for a malformed header or a secrets-mount precondition) is part of that answer, and 404 comes only after it. If-None-Match: * makes the write create-only: it creates the object when none exists and returns 412 when one does, and the check and the write are one atomic step, so of several concurrent first-creates exactly one wins. An If-None-Match list of validators returns 412 when one matches the object’s current ETag and proceeds otherwise; If-Match returns 412 when none matches. For a binary value the ETag is the content hash that GET serves. With both headers, If-Match is evaluated first. A secrets-mount value is never readable and has no ETag, so there only If-None-Match: * is accepted (412 when the slot exists, with the backend untouched); a malformed header, If-Match or any other If-None-Match is 400 invalid-input, answered after the authority check.

If-Match: * asks whether a current representation exists, the same test If-None-Match: * uses, so a caller who may write an object but not read it can pass it. A list of validators needs a representation the caller can read.

DELETE /v1/<obj> follows the same rule, evaluated in the delete’s critical section after the existence and delete-authority checks: If-Match with a stale validator is 412 and the object stays, a binary value compares against the content hash GET serves, repeated If-Match lines combine, and If-None-Match: * on an existing object is 412. An absent object is 404, and a caller who may not delete gets 403 whatever the headers say. In a coupled object-binding mode the caller’s authority over the bound verbs is checked before the precondition, so a caller who may delete the object but not a verb bound to it gets 403. DELETE of a secrets-mount value takes the mount’s rule: the precondition is checked after the authority gates and before the backend is purged, and the purge and the reference removal run in the same critical section, so a refused request leaves the secret in place.

Where a verb makes the write, the host has no stored tag to compare. A PUT, PATCH, POST or DELETE that an accessor verb serves (:update, :set, :create, :delete), and a verb-route action (POST /v1/<obj>:<action>, including Prefer: respond-async), is refused with 400 invalid-input when it carries any If-Match or If-None-Match, well-formed or not. The verb does not run and no idempotency record is written. The authentication, delegation and anonymous-mutation checks answer first, so a caller they refuse gets their 401 or 403. To guard such a write, put a version field in the body, or use set-at-if from a verb. A read that a verb serves evaluates both headers against the sha256 ETag of its output: GET on an accessor-served object (:get, :list) and GET /v1/<obj>:<function> answer 412 for an If-Match that does not match, 304 for an If-None-Match that does (a W/ form, a list or *), and 400 for a malformed value, after the verb’s own policy has allowed the call. GET /v1/<obj>?meta=<facet> evaluates them after its read or manage check: it has no ETag, so a list in If-Match is 412 and * passes, and * in If-None-Match is 304. An event-stream subscribe (Accept: text/event-stream) with either header is 400 once the caller may read the topic. With RESTACT_ACCESSOR_DISPATCH=off the bare path is the plain data plane described above. On a secrets-mount path no method dispatches to an accessor, whether it is deployed at the slot pattern or at an ancestor: the data plane serves GET, PUT and DELETE, and PATCH and POST answer 405.

Every 405 carries an Allow header listing the same methods OPTIONS reports for that path, whether the mismatch is a wrong method on a verb, on a verb property, or on a plain object. A method sent to a verb that is not deployed is 404, the same answer OPTIONS gives.

On the verb plane, If-Match beyond PUT …/code and create-only If-None-Match: * on POST /v1/modules need the verb-conditional-requests feature (see Verb properties and Deploy a verb).

Idempotency

Section titled “Idempotency”

For retry-safe actions, send an Idempotency-Key header. A repeat by the same authenticated caller on the same route replays the first result, whatever the body. While the first request is still running, a repeat answers 409. The key is scoped to the caller and the route, so the same key on another route runs normally. Anonymous callers share one identity, so their key is ignored and the action just runs.

Async operations

Section titled “Async operations”

An action POST that carries Prefer: respond-async returns 202 Accepted with Location: /operations/{id}. Poll the operation resource; DELETE cancels it:

Both routes are owner-scoped: another tenant’s operations are invisible (404 on the item route, absent from the listing). The listing is unpaginated by design — the table is bounded and owner-filtered (feature token operations-listing). A U+0000 in a recorded error’s code or detail is shown as U+FFFD.

Verb subscriptions are read-gated (verb-subscriptions-read-gate)

Section titled “Verb subscriptions are read-gated (verb-subscriptions-read-gate)”

POST /v1/subscriptions {"topic","target"} requires read on the topic object at registration and at every delivery. Registration on a topic the caller cannot read, or that does not exist, is 404 not-found (the same refusal SSE gives; create the topic object first). A topic the caller can read but the subscription’s subject-only registrant cannot (readable only through a role, group, scope or claim matcher) is 403 forbidden. Each delivery is re-checked against the registrant’s current read authority, before the min gap and the quota; a refused delivery is skipped, never retried, invisible to the registrant, and logged as one content-free warn line. An onDelete is checked against the pre-delete snapshot and skipped without one (on PostgreSQL every onDelete delivery is skipped). Advertised as verb-subscriptions-read-gate alongside verb-subscriptions; it cannot be turned off.

Operator clean-reset (POST /admin/reset)

Section titled “Operator clean-reset (POST /admin/reset)”

Returns a running host to its post-bootstrap state — equivalent to stopping the process, deleting the data dir, and starting again, without restarting. Wipes all tenant state: deployed verbs + blobs, object data + listing, schedules/subscriptions, event replay rings + the durable event log, quota tallies, the idempotency cache and operations table — then re-runs the same idempotent startup bootstrap (which seeds the example content only with RESTACT_EXAMPLES=1, and always registers the script runners). The SSE event-id counter deliberately survives, so a client reconnecting with its old Last-Event-ID replays exactly the post-reset events; live SSE streams end and EventSource clients auto-reconnect.

OFF by default. Enable with RESTACT_ADMIN_RESET=<matcher-list> (the canonical subject matchers, e.g. role:admin, or public for an intentionally-open localhost host — see Configuration); unconfigured, the route answers 404 like any unknown path and the admin-reset discovery feature token is omitted. With auth configured, an anonymous POST is 401 (the anonymous-mutation rule) and a non-matching principal 403.

Name a dedicated operator subject in RESTACT_ADMIN_RESET (and in RESTACT_ADMIN_REOWN, below), one that is used for nothing else. The gate matches the caller’s subject, so any full bearer minted under that subject carries the same power, for example a user bearer that a plugin minted for it. Only delegated and path-scoped tokens are refused.

Operator ownership recovery (POST /admin/reown)

Section titled “Operator ownership recovery (POST /admin/reown)”

Ownership is fixed, so nothing an owner has can change hands by an ordinary write. If an owner leaves, their verbs and roots would freeze; this route recovers them. It moves the verbs and objects that one subject owns, under one path, to another subject.

OFF by default. Enable with RESTACT_ADMIN_REOWN=<sub:…,sub:…>: sub: matchers only, none of them sub:anonymous, and authentication must be configured. Anything else leaves the route off and prints a boot warning: line. Unconfigured, the route answers 404 (OPTIONS too) and discovery omits the admin-reown feature token. Name a dedicated operator subject here: a full bearer minted under that subject has the same power (only delegated and path-scoped tokens are refused).

Gate order: off 404 (whatever the body size); then the 64 KiB body cap, 413, before authentication (so an anonymous caller or a non-operator also gets 413 for an oversized body); then an invalid credential 401; a path-scoped sub-token 403; anonymous 401; a caller matching no configured subject 403; then the body, 400 invalid-input when invalid.

A body is 400 when it has an unknown member; when from or to is missing, not a string, empty after trimming, has leading or trailing whitespace, or contains a control character; when from == to; when to is anonymous or begins client:; when path is missing or not a data-plane object path (no leading /, no v1/ prefix, no :, no @ segment, no . or .. or empty segment, nothing at or under the reserved delegation paths); or when subtree or dryRun is not a boolean. from: "anonymous" is allowed.

When the server is down or the route is off, restactd reown runs the same move offline and prints this 200 body with --json.

The request body is limited to about 64 KiB: a larger one is 413 (and with the route off, 404).

What moves, and what does not:

  • Selection is literal and owner-filtered: an object whose path equals path (or, with subtree, lies under it) and whose stored owner is from, and a stored verb deployment whose route is anchored at path (or, with subtree, under it) and whose owner is from. A route’s anchor is its leading run of literal segments, so ws/acme/{id}:onCreate is anchored at ws/acme. Native verbs are never selected.
  • A moved verb takes the new owner, loses runs_as=owner and the invoker grant, and, if it is a lifecycle hook (onCreate, onChange, onDelete), is paused: it does not fire until its new owner redeploys its code. The new owner re-opts in with their own credential. Policies are kept.
  • A moved object changes only its owner. No hook fires and no event is published.
  • Not moved: schedules and subscriptions (they keep firing as their registrant), grants and sub-tokens (the subject’s own credentials), and secret-mount slots (skipped and counted in skipped.secretSlots).
  • dryRun: true validates, selects and reports, and writes nothing.
  • Each item is atomic; the call as a whole is not. A part-way store error is 500 store-error carrying the verbs, objects and skipped counts already done, and a retry finishes the move. A PUT …/policy that races a reown of the same verb answers 409 conflict.
  • Each non-dry-run call writes one operator-log line on restact.mgmt. A call that stopped part-way (a store error, or a panic in the move) ends its line with (stopped part-way); a completed call’s line never does. The line is written even when the client disconnects mid-call.

Durable checkpoint (POST /admin/checkpoint)

Section titled “Durable checkpoint (POST /admin/checkpoint)”

Copies the durable store to <checkpoint-dir>/checkpoint-<ts>-<seq> — a best-effort point-in-time snapshot (crash-stop consistency). The snapshot of a filesystem store is itself a valid store root: restore by pointing RESTACT_DATA_DIR at it (or copying it over a wiped root). Around each run the host publishes checkpoint-started / checkpoint-finished {ok, snapshot, durationMs} on the reserved @host/checkpoint topic — guests can subscribe (verb subscriptions, or SSE on /v1/@host/checkpoint as any authenticated principal) but can never publish there.

OFF by default. Enable with RESTACT_ADMIN_CHECKPOINT=<matcher-list> (gating exactly as reset: unconfigured → 404 + no admin-checkpoint token; anonymous under auth → 401; non-matching → 403). RESTACT_CHECKPOINT_INTERVAL_SECS=<n> additionally runs an interval loop (floored at 30 s) — that alone also advertises the token. Retention: RESTACT_CHECKPOINT_KEEP newest snapshots (default 8). Snapshots survive POST /admin/reset. A checkpoint and a reset never overlap: one that finds the other running (or another checkpoint) is refused 409 and never queued, and an interval tick that finds the lock held is skipped. The checkpoint request is exempt from RESTACT_REQUEST_TIMEOUT_MS.
