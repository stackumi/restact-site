Conformance suite

restact-conformance is a black-box test runner for REST:ACT servers. It reads a server’s discovery document, checks the behavior every server must have, then checks each optional feature the server advertises. Use it to test restactd, or to test a server you are building.

The source is in conformance/. The suite is the executable form of the requirements in the REST:ACT specification, and it also serves as the integration test for the reference host.

Run it against restactd

Section titled “Run it against restactd”

From a checkout, one script builds the host, the runner and the fixture verbs, then runs the suite against both executor backends: the in-process executor and the per-request process-isolation worker.

If port 8080 is taken, set RESTACT_TEST_PORT to a free port. The script starts its own host, so stop any running one first. make conformance runs the same script.

Run it against another server

Section titled “Run it against another server”

Build the runner and point it at the server:

The runner calls GET /.well-known/restact first and exits with status 2 if it cannot reach the server. Without RESTACT_BASE_URL it uses http://127.0.0.1:8080.

The runner deploys fixture verbs through POST /v1/modules before it checks anything. A server that deploys verbs some other way can pre-deploy the same verbs, named conf:*, and set RESTACT_CONFORMANCE_NO_SETUP=1. The setup function in conformance/src/main.rs lists them.

VariablePurpose
RESTACT_BASE_URLThe server to test. Default http://127.0.0.1:8080.
RESTACT_CONFORMANCE_TOKENA bearer token for the default client, which deploys the fixtures and drives most checks.
RESTACT_CONFORMANCE_NO_SETUPSet to 1 to skip fixture deployment and use verbs already deployed.
RESTACT_FIX_DEMO, RESTACT_FIX_WC, RESTACT_FIX_NETPaths to the fixture components. Each unset RESTACT_FIX_* variable falls back to its file in ../share/restact-conformance/fixtures/ next to the runner’s binary (the layout of the release tarball); a variable that is set always wins. A check that needs one exits with status 2 if the variable is unset (with no such directory) or the file is unreadable.
RESTACT_FIX_COUNTERA JavaScript fixture, with the same fallback to counter.js. Checks that need it are skipped when neither is available.
RESTACT_CONFORMANCE_REQUIRE_FEATURESA comma-separated list of feature tokens. A listed feature that the server does not advertise fails instead of being skipped.

The authorization checks need one token per subject, signed so the server accepts them. Without a token, the checks that use it are skipped.

VariableSubject
RESTACT_TOKEN_ALICE, RESTACT_TOKEN_BOBalice and bob. The delegation checks need these literal subjects.
RESTACT_TOKEN_OPERATORThe operator named for the re-own checks.
RESTACT_TOKEN_GROUPSSubject gina with a groups claim that includes builders.
RESTACT_TOKEN_CLIENTA subject that starts with client:, for the delegated client-actor checks.
RESTACT_CONFORMANCE_SECRETS_PATHA path under the secrets mount, for the secret-value check.

How checks are gated

Section titled “How checks are gated”

Each check has an id, a level and a reference to a section of the specification.

LevelMeaning
MustThe server must behave this way. Every server is checked.
ShouldA recommendation. A failure is reported as a warning.
OptionalRuns only if the server advertises the named feature token. Otherwise it is skipped.

The core checks cover addressing, verb resolution, the function and action methods, problem-document errors, the three resource limits, and the discovery document itself. Optional checks are tied to the feature tokens in the features table: composition, the data plane, conditional requests, async operations, lifecycle hooks, events, schedules, the scripting tiers, delegated tokens, the admin plane and more. A server that advertises nothing optional is checked against the core only.

This gating is how the suite stays useful for a small server. A feature the server does not claim is never counted against it, and a feature it does claim has to work.

Read the results

Section titled “Read the results”

The runner prints the target and the advertised features to stderr, then one line per check on stdout. Example output, with a made-up failure:

ResultMeaning
PASSThe behavior matched.
FAILA must-level or advertised-feature check did not match. The line gives the status and a body excerpt.
WARNA should-level check did not match.
SKIPThe server does not advertise the feature, or a token or fixture was not supplied.

The last line is a summary such as 120 passed, 0 failed, 1 warned, 30 skipped. The exit status is 0 when nothing failed, 1 when any check failed, and 2 when the runner could not start. A skipped or warned check does not change the exit status.

The id names the area: CORE/ for the mandatory core, OPT/ for an optional feature, and AUTHZ/ for the authorization checks, which need tokens. A few checks use their own prefix: ACL/, COMPOSE/, CONS/, DISC/, IDENT/, REC/ and REG/. Each id maps to a section of the specification, so a failing line points at the requirement.

Limits

Section titled “Limits”

The suite does not check requirements with no observable HTTP behavior, such as a GET never changing state or the use of TLS. It does not validate OpenAPI documents. python3 openapi/scripts/validate.py separately checks the x-restact extension schema and the example OpenAPI documents in openapi/examples/.
