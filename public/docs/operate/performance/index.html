Performance

This page gives measured latency, throughput, cold-start and memory figures for restactd, the command that produced them, and what to size from them. The numbers describe one machine on one day. Treat them as an order of magnitude and run the benchmark on your own hardware before you plan capacity.

What was measured

Section titled “What was measured”
  • Hardware: AMD Ryzen 7 5800X (8 cores, 16 threads), 31 GB RAM, NVMe SSD, Linux 7.2.
  • Build: restactd release build, no optional features, Rust 1.99.1. Filesystem store. The data directory and the compile cache were on tmpfs (RAM), under /tmp, so disk speed is not part of these figures.
  • Load generator: oha 1.16 on the same machine, so the figures include loopback HTTP and exclude any network.
  • The verb: every tier runs the same small job, counting the words of a 43-byte body. It is deployed as an action and called with POST, so no response is served from a cache. The compiled verb is the Rust SDK word-count-sdk example; the JavaScript and Python verbs are one-line invoke functions.
  • Shape of a run: 20,000 requests at concurrency 8 after a 500-request warm-up. Each figure is the median of 3 runs.

Other sessions were using the machine while these runs went on. The one-minute load average, sampled with every measurement, ranged over these bands: 7.6 to 8.5 for the in-process latency runs, 13.3 to 23.4 for the process-isolation latency runs, 4.6 to 8.4 for the cold-start runs (repeated on a quieter machine than the other sections), and 9.6 to 34.2 in process and 20.8 to 44.5 under process isolation for the memory runs. A quiet machine should do better, and the process-isolation rows and the memory peaks are the most affected.

In process, a call costs well under a millisecond for every tier. The JavaScript verb is slower than the Python one in this test; both run inside a shared runner component, and the measurement does not say why. A verb that does real work, calls objects or composes other verbs costs more than this trivial one.

Process isolation starts a worker process for every request, and the worker loads its components before it runs. That start-up dominates the figures above. Python is likely the slowest because its runner component is the largest, 5.9 MB against 1 MB for JavaScript. This is the price of the isolation boundary; see Storage and scaling for when to pay it.

Cold start

Section titled “Cold start”

A fresh upload is a new content hash, so the host has not seen it before. The compile cache is the on-disk cache described under RESTACT_COMPILE_CACHE_DIR in the configuration reference.

First call of a stored verb after a restart, process isolation (Rust / JavaScript / Python)21 / 26 / 56 ms36–89 / 203–464 / 732–1,796 ms

In process, the first call after an upload is within 0.3 ms of the second. The cache matters in two places. It cuts host start-up in process from about 0.9 s to about 0.06 s, and under process isolation it saves each worker from compiling the runner: with the cache off, a JavaScript call took 190 to 370 ms and a Python call 0.7 to 1.6 s in our runs, on every request. With process isolation, leave the cache on.

Memory does not grow evenly: a few concurrent calls cost more each than many, because the first calls set up buffers the later ones reuse. These verbs allocate almost nothing of their own. A verb that holds a large input, builds a large result or raises its mem_mb costs that much more.

Reproduce

Section titled “Reproduce”

Install oha, build the JavaScript and Python runners if you want those tiers, then run the benchmark from a checkout:

The arguments are the request count, the concurrency and the number of runs. The script builds the release host and the Rust verb, starts its own host on RESTACT_TEST_PORT, runs the three sections (latency, cold start, memory) in process and under process isolation, writes every sample with the one-minute load average to BENCH_OUT, and prints the medians. A tier whose runner component is missing is skipped. Run it on an idle machine; the load column in the raw file tells you when it was not.

Sizing

Section titled “Sizing”
  • Memory, in process. Start from the idle host, about 40 MB. The measured peaks at 8 concurrent calls were 59 MB (Rust), 54 MB (JavaScript) and 49 MB (Python), which is 10 to 17 MB above idle, or about 1.2 to 2 MB a call. At 64 calls the peaks were 67, 78 and 93 MB, about 0.4 to 0.8 MB for each call beyond the first. Per tier, a rule that covers the 8-call peaks is 40 MB plus 2 MB for each call you expect to run at once for compiled verbs (59 MB at 8), and 1.5 MB for JavaScript (54 MB) and Python (49 MB); add whatever your own verbs allocate. The per-verb mem_mb limit is a ceiling for a single call, not a reservation: RESTACT_MAX_VERB_MEMORY_MB sizes address space, not resident memory. Set a container memory limit well above the figure you compute, since the peaks are sampled and short-lived.
  • Memory, process isolation. Every concurrent call is a worker process of its own, on top of the host. A Python worker was seen at up to about 50 MB while it ran. That is an upper bound, because the pages a worker shares with the host are counted twice. Multiply by your concurrency and add the host before you set a memory limit; this page has no clean measurement of it.
  • Concurrency. RESTACT_MAX_INFLIGHT (default 256) caps requests in flight across the host. Raise it only after you have confirmed that memory and the request timeout hold at the new value.
  • Process isolation, throughput. In this test a call cost 16 ms (Rust), 26 ms (JavaScript) or 92 ms (Python) at the median, and the host served 490, 310 and 82 calls a second at concurrency 8. Size for the tier you use, not for a single figure. If you need more, run more hosts against a shared database rather than raising the in-flight cap; see Storage and scaling. RESTACT_WORKER_TIMEOUT_MS should stay well above the cold figures in the cold-start table.
  • Disk. The compile cache is bounded by RESTACT_COMPILE_CACHE_MAX_BYTES (2 GiB by default). Put it on a persistent volume (these runs used tmpfs) so a restart does not recompile the runners.
  • Fuel and wall time. Per-verb fuel and wall_ms limits bound the work a single call may do. The figures above are for calls that finish in microseconds, so they say nothing about where those limits should sit for your verbs.

Caveats

Section titled “Caveats”
  • One machine, one workload, one small body. Verbs that read or write objects, compose other verbs, call out over the network or return large bodies behave differently, and the store matters: these runs used the filesystem store and no authentication.
  • The load generator shared the machine with the host. Latency under a separate client and a real network will be higher.
  • Host start-up is timed from just before the process is launched to the first healthy answer to a curl poll every 10 ms, so it includes up to one poll. The cache-on figures held within about 25% across three repeats of the cold-start set. The cache-off figures under process isolation varied two to three times with machine load, so they are given as the range of the three repeat medians. The advice does not change: keep the compile cache on.
  • Other work was running on the machine, as stated above. The process-isolation latency rows were taken at a load average of 13 to 23.
  • Memory under process isolation is not tabulated. Workers live for a single request, and the 20 ms sampling misses most of them, so the peaks it produced were not stable enough to publish. Measure it on your own deployment with your own verbs.
  • The PostgreSQL store, OpenTelemetry and authentication add cost that this page does not measure.
