Storage and scaling

restactd keeps deployed verbs, object data, registrations and operation state in a store. You pick the store, and separately pick how verbs execute: in the host process or in a worker process per request. This page covers both choices, running several nodes against one PostgreSQL, size limits and backups.

Pick a store

Section titled “Pick a store”
StoreSelect withSurvives restartNodes
Memorynothing setNo1
FilesystemRESTACT_DATA_DIR=/var/lib/restactYes1
PostgreSQLRESTACT_DATABASE_URL=postgres://…YesMany

With neither variable set, everything lives in memory and is lost when the process exits. That is the right setting for development and tests, and the wrong one for anything you intend to keep.

If both variables are set, PostgreSQL wins.

Filesystem

Section titled “Filesystem”

The store is content-addressed: verb components and binary values are kept by hash, and deployments, registrations and object data sit beside them. The directory must exist or be creatable and be writable by the server’s user.

If the directory cannot be opened (not writable, or a corrupt deployments.json, registrations.json or format.json), the host refuses to start. It never falls back to memory, because that would lose every write at the next restart.

The filesystem store belongs to one host process. The host takes an exclusive lock on locks/data-dir.lock in the data directory before it opens the store and holds it until it exits, so a second host on the same directory refuses to start:

The text in that file only names the holder; the lock decides. Process-isolation workers inherit the lock, so the directory stays locked until the last worker of a killed host has exited. If the filesystem cannot lock (some network filesystems), the host logs one warning and serves without the lock, except under RESTACT_ISOLATION=process, where the host refuses to start. Use PostgreSQL to run more than one node.

PostgreSQL

Section titled “PostgreSQL”

The PostgreSQL backend is optional and compiled in with a Cargo feature. Build the binary or image with it:

A binary built without the feature that is given RESTACT_DATABASE_URL refuses to start, so a missing feature never leaves nodes on isolated stores.

The connection is encrypted by default. The URL’s sslmode defaults to require, and the modes that can silently downgrade to plaintext (disable, allow, prefer) are refused:

For a database that is reached over an untrusted network use sslmode=verify-full with a CA file. Set RESTACT_PG_ALLOW_PLAINTEXT=1 only for a loopback or throwaway database such as the one in docker-compose.postgres.yml. A bad URL is fatal at startup. A transient connect failure (a database that is still starting) is retried up to RESTACT_PG_CONNECT_ATTEMPTS times (default 5) within RESTACT_PG_CONNECT_TIMEOUT_SECS (default 180) so a node does not crash-loop.

Tuning variables, with defaults:

RESTACT_PG_STATEMENT_TIMEOUT_MS30000Server-side statement_timeout; bounds a stuck write or a hot-key lock wait.

PostgreSQL active-active

Section titled “PostgreSQL active-active”

With RESTACT_DATABASE_URL set, you can run any number of identical nodes behind a load balancer. They share one database, and these behaviors span the cluster:

  • Object writes are serialized with advisory locks, so concurrent writers on different nodes do not lose updates.
  • A schedule fires once cluster-wide, and another node takes over if the firing node dies.
  • Idempotency keys and asynchronous operations (202 plus a poll URL) work from any node.
  • Server-sent events and subscriptions are delivered through the database. The event log is bounded in bytes and rows at every insert (migration 0010_event_log_bounds.sql adds the ledger and the per-topic trim marks). A subscriber whose cursor points at trimmed events gets a gap event, as does one that resumes across a POST /admin/reset. Set both bounds to the same values on every node, since each publish applies its own node’s. Subscription delivery is claimed through one cursor per subscription (migration 0011_subscription_cursors.sql), so that state is bounded by the number of live subscriptions and nothing prunes it. A subscription is delivered or skipped at most once per event, in order, across the cluster; once any node has decided an event, no node delivers an earlier one for that subscription. An event published before the subscription was registered is never delivered, and a node attempts only events published after it connected, so a restart delivers nothing published before it. Delivery is live-only: an event that no live node attempts is not delivered later.

Every node needs the same authentication settings. For HS256, set the same RESTACT_JWT_SECRET on all of them so a token issued for one node validates on the others. The fuel and call quotas are shared through the database. The storage quota (RESTACT_QUOTA_STORAGE_BYTES) and the egress quotas are tallied in each process, so on N nodes their effective cap is N times the configured value.

Behavior when the database misbehaves:

  • An idempotency claim fails closed: the request gets 409.
  • The cross-node quota read fails open, and the host logs restact.pg.quota read_failed fail_open=true.
  • /readyz runs a SELECT 1. Use it as the readiness probe so a node that lost its database link is taken out of rotation. Use /healthz as the liveness probe. See Observability.

Listings and obj.query scan a path prefix as a byte range (object_path ~>=~ $lo AND object_path ~<~ $hi), and the built-in object_attrs_path_pattern index (text_pattern_ops) serves it. Do not add a partial index of the form ... WHERE object_path LIKE 'notes/%', which the older migration comments suggested. The range bounds and the ordering property arrive as bind parameters, and PostgreSQL may switch a prepared statement to a generic plan after a few executions. Under a generic plan the planner cannot prove a literal index predicate from those parameters, so a partial index cannot be relied on. An expression index on the ordering property (attrs->>'published') fails the same way, because the property name is bound too. Both were checked with EXPLAIN on PostgreSQL 16 under plan_cache_mode = force_generic_plan: every plan used object_attrs_path_pattern.

Size max_connections on the database for the whole fleet: at least N × (RESTACT_PG_POOL_SIZE + RESTACT_PG_LOCK_POOL_SIZE + a few connections for event listening), plus up to RESTACT_MAX_WASM_INFLIGHT more per node under process isolation. For a large fleet put PgBouncer in front in session mode; transaction mode breaks the session advisory locks.

Pick an executor

Section titled “Pick an executor”

The store decides where state lives. The executor decides where verb code runs. Both executors run the same components with the same limits, and the full conformance suite passes on each.

In-process (default)Process isolation
Select withnothingRESTACT_ISOLATION=process
Where a verb runsA Wasmtime instance inside the host processA fresh worker process per request, the same binary re-executed
Protects againstEverything the sandbox enforces: no ambient authority, capability confinement, fuel, wall-clock and memory limitsThe above, plus a separate address space per request: one request cannot read another request’s memory or the host process’s
CostsLowest latencyA process spawn and engine start per request, no worker pool
NeedsNothingA durable store: RESTACT_DATA_DIR or RESTACT_DATABASE_URL. Without one, the host refuses to start (exit 1) and names RESTACT_ISOLATION, RESTACT_DATA_DIR and RESTACT_DATABASE_URL

Choose process isolation when untrusted tenants share the host. Choose in-process when verbs come from people you trust or when per-request latency matters more than the extra boundary.

Details of process isolation:

  • The worker re-opens the same store as the parent, so composition, shared budgets and capability attenuation all behave as they do in-process. The parent debits quota and fuel and kills a worker that passes RESTACT_WORKER_TIMEOUT_MS (default 30000).
  • Workers cache compiled components on disk so they do not recompile on every request. The cache lives in RESTACT_COMPILE_CACHE_DIR (default under $XDG_CACHE_HOME/restactd or $HOME/.cache/restactd), each entry is authenticated with an HMAC before loading, and RESTACT_COMPILE_CACHE_MAX_BYTES (default 2 GiB) caps it. In a container, mount a volume there or accept a cold cache after each restart. See Isolation.
  • Workers write diagnostics to stderr only; the parent captures the response from stdout.

Backup and restore

Section titled “Backup and restore”

A filesystem store is backed up by taking a snapshot: a directory that is itself a valid store root. PostgreSQL is backed up with the database’s own tools. Both are covered below, along with what a snapshot leaves out and why you should only restore snapshots you trust.

Filesystem store: take a snapshot

Section titled “Filesystem store: take a snapshot”

restactd checkpoint writes a verified snapshot. It reads the same RESTACT_* variables as the server, so run it with the same RESTACT_DATA_DIR:

The snapshot path is the only thing on stdout (--json prints {"snapshot": ..., "mode": "live"|"offline", "durationMs": ...} instead). The command checks the data directory’s lock to decide how to work:

  • With no server running, it copies the store itself and holds the lock while it does. Nothing else writes meanwhile, so the snapshot is consistent. This needs no configuration.
  • With a server running, it asks that server to do the copy by sending POST /admin/checkpoint to RESTACT_BIND. The server must have RESTACT_ADMIN_CHECKPOINT set (otherwise the command exits 3), and RESTACT_BIND must be an IP address and port such as 127.0.0.1:8080 or [::1]:8080, because the bearer token is sent to exactly one address (0.0.0.0 and [::] map to loopback). Under authentication the command needs a bearer token on stdin, never on the command line:

With OIDC, pipe in a token from your issuer instead. The command verifies what the server wrote before it reports success.

--out DIR puts the snapshot in DIR, which must not exist yet and must not lie inside the data directory’s store files. --timeout bounds the live request (default 15 minutes, a whole number followed by s, m, h or d). After a timeout the server still finishes the snapshot and announces it on @host/checkpoint.

ExitMeaning
0Snapshot written and verified.
1Failed: an I/O error, a snapshot that fails verification, a server error.
2Usage or configuration: a bad flag, --out already exists, no RESTACT_DATA_DIR.
3Not available: PostgreSQL is configured, the server has no checkpoint endpoint, or the filesystem cannot lock.
4The server refused the bearer token (401 or 403).
5A server holds the directory but nothing answers at RESTACT_BIND, or --timeout passed.
6Busy: another restactd command holds the directory, or the server is running a reset or another checkpoint.

You can also call the endpoint yourself, for example from a cron job on another machine. It is described under HTTP API. From another machine, restact admin checkpoint makes the same request (see the command line reference).

Interval checkpoints and retention

Section titled “Interval checkpoints and retention”

A host can snapshot itself on a timer, with or without the HTTP endpoint:

RESTACT_CHECKPOINT_INTERVAL_SECS has a minimum of 30 seconds. RESTACT_CHECKPOINT_KEEP keeps the newest N snapshots (default 8, 0 keeps all). The command applies the same retention when it writes into the checkpoint directory, but not when you use --out.

Snapshots land in <data dir>/snapshots/checkpoint-<unix-time>-<seq>. Set RESTACT_CHECKPOINT_DIR to put them elsewhere. A stopping host finishes a checkpoint that is already copying, with no cap; see Containers and Kubernetes for the grace period. A live snapshot is a crash-stop image of a running store, the same state the host would recover to after a crash. That directory is on the same disk as the store by default, so copy snapshots off the machine on a schedule. Two hosts must not share one RESTACT_CHECKPOINT_DIR: each sweeps the directory’s .partial-* entries when it boots, and each prunes the other’s snapshots.

Copy by hand

Section titled “Copy by hand”

With the host stopped, copying the data directory (or the store files in it: blobs/, state/, deployments.json, objects.json, registrations.json, grants.json and format.json) gives you a valid snapshot. Do not copy a running host’s directory with cp or rsync: the copy races every write.

A damaged objects.json is never read as an empty index. The host refuses to start on one and names the file, and a running host answers any request that needs the index (a listing, a query, a write of a new object, a delete) with a 503 unavailable problem, leaving the file as it is. A verb’s obj.query fails the same way instead of returning an empty page. Under process isolation, any verb write is refused while the index is damaged, not only a write of a new object. Under RESTACT_CONSISTENCY=atomic-invocation, a verb’s write set is discarded and the failure logged, as that mode already does for a failed commit. Restore the file from a snapshot, or repair it, before starting the host again. A missing objects.json is an empty index.

Filesystem store: restore

Section titled “Filesystem store: restore”

Stop the host first. restactd restore refuses to run while a server or another restactd command holds the data directory (exit 6).

The command copies the snapshot into a staging directory inside the data directory and verifies it. It checks that every file parses, that every blob matches its hash, and that every blob a deployment or object refers to is present. Only then does it move the current store aside into pre-restore-<unix-time> and move the snapshot’s files into place. The printed path is that pre-restore-<unix-time> directory, which is itself a complete store, so restactd restore --from that path undoes the restore. The command never deletes it; remove it when you no longer need it. A snapshot that fails verification leaves the data directory untouched (exit 1).

If a restore is cut off partway, the data directory holds RESTORE-IN-PROGRESS.json and the host refuses to start. Run restactd restore --from with the same snapshot again: it rolls back the interrupted run and restores afresh.

restore creates a missing data directory, so it also restores onto a fresh volume. It refuses (exit 2) a directory that holds files that are not part of a store, so a wrong RESTACT_DATA_DIR is not overwritten. --from may not be the data directory or lie inside its store files. The same exit codes as checkpoint apply, minus 4 and 5.

To restore by hand, stop the host and either set RESTACT_DATA_DIR to the snapshot directory, or empty the data directory’s store files and copy the snapshot’s over them. Keep the old files until the restored host answers. Because a snapshot is a valid store root, the first option works as it stands, but the host then writes into the snapshot, so copy it first if you want to keep it.

Test a restore before you need it. Restore a snapshot into a scratch directory, start a host against it on another port, and check that GET /v1 and a verb you care about answer.

Containers and Kubernetes

Section titled “Containers and Kubernetes”

In the image the server is the main process, so restore runs in a one-off container on the same volume while the server’s container is stopped. The same goes for an offline checkpoint:

On Kubernetes, scale the Deployment to zero, run a Job that mounts the same PersistentVolumeClaim and runs restactd restore --from /data/snapshots/<name>, then scale back up. The image entrypoint is restactd, so the Job needs only args: ["restore", "--from", "/data/snapshots/<name>"]. A running pod can be checkpointed with kubectl exec -i <pod> -- restactd checkpoint --token-stdin, provided the pod has RESTACT_ADMIN_CHECKPOINT set and you pipe a bearer token in if it uses authentication. A bind mount must be writable by uid 65532 (see Run with Docker).

A stopping host finishes a checkpoint that is already copying, with no cap, and starts no new interval checkpoint. If the grace period is shorter than the copy, the container is killed mid-copy: that snapshot is lost, the store is untouched, and the next boot removes the .partial-* directory. Size the grace period for your store: docker stop -t <seconds>, Compose stop_grace_period, or Kubernetes terminationGracePeriodSeconds.

What a snapshot leaves out

Section titled “What a snapshot leaves out”

A snapshot holds the store: deployed verbs and their records, objects, registrations (including schedules and subscriptions) and grants. It does not hold:

  • page-token.key, the key that seals page tokens and query cursors. A restore makes a new one, so outstanding pageTokens and any query cursor a verb stored stop working. Nothing else depends on it. To rotate the key on purpose, stop every node and delete the file. Never delete it while a node runs: that node’s isolation workers fail every invocation until it restarts. The data directory must support hard links, or the host refuses to boot.
  • The compile cache (RESTACT_COMPILE_CACHE_DIR). Verbs recompile once after a restore.
  • locks/, which belongs to the directory and not to its contents.

JavaScript and Python verbs come back bound to the runner build recorded in their deployment record, and schedules come back with their stored last-fire time, so a schedule fires at most once to catch up.

A snapshot is authority

Section titled “A snapshot is authority”

A snapshot carries owners, $policy objects, grants, deployment records (with their runs_as and capability settings) and verb code. Restoring one trusts whoever wrote it. Verification shows that a snapshot is intact and consistent, not that it is harmless. Restore only snapshots you took yourself, and keep them where only operators can write. Restored verbs still run inside the sandbox; what their records grant is the question of trust.

PostgreSQL

Section titled “PostgreSQL”

restactd checkpoint and restactd restore exit 3 when RESTACT_DATABASE_URL is set, without connecting to the database, and point here. POST /admin/checkpoint is also not available on PostgreSQL. Use the database’s own tools: pg_dump and pg_restore, WAL archiving, or your provider’s snapshots. Back up the whole database; restactd keeps nothing important outside it.

To restore, stop every restactd node first. Restore into an empty database (pg_restore --clean --if-exists --dbname=...), then start the nodes. A node that keeps running against a database you are restoring serves stale caches and can write into the half-restored data.

The page-token key is the host_keys row named page-token; it travels with the dump. To rotate it, stop every node and delete the row.

Audit a store for ancestor claims

Section titled “Audit a store for ancestor claims”

restactd audit ancestry reads a store and lists what the ancestor-claim guard would leave in place. It reads the same RESTACT_* variables as the server (RESTACT_DATA_DIR, or RESTACT_DATABASE_URL on a PostgreSQL build, the auth, RESTACT_OBJECT_BINDING and RESTACT_POLICY_INHERITANCE settings, RESTACT_ADMIN_REOWN, and the bootstrap file settings), prints ancestry-audit: lines on stdout and exits. Run it with the server’s environment and working directory: the environment decides what is in scope, and the bootstrap files (docs/, site/examples/, the example .wasm files) are found by the same relative paths the server uses.

It reports three things:

  • Claimed ancestors. A stored object with at least one descendant owned by someone else. The line names the ancestor and its owner, the descendant and other-owner counts, and whether the ancestor hosts verbs. class says whether the ancestor was created after its descendants, before them, or unknown (a missing stamp, the same second, or a mix). It rests on one-second wall-clock stamps, so treat it as a hint. An ancestor whose owner matches RESTACT_ADMIN_REOWN is listed as exempt and is neither counted nor reflected in the exit code, since an operator-owned ancestor is not a squat.
  • Precedence changes. Same-level pattern pairs for one verb, such as px/{id}:v and {id}/leaf:v, where the pattern with the leftmost literal wins but literal count alone would tie or pick the other pattern. The line names the deploy-order, route-order and leftmost-literal winners; the leftmost-literal winner is the pattern served.
  • Orphan definitions. A verb definition whose anchor object is absent or owned by someone other than the definition’s owner.

Claims and orphans belong to the ancestor-creation guard, so they are listed and counted only when the guard is on in the audit’s own environment: authentication configured, and either a coupled RESTACT_OBJECT_BINDING mode (strict is the default under HS256) or RESTACT_POLICY_INHERITANCE. Orphans are in scope only under a coupled mode. When the guard is off the audit prints one ancestry-audit: note: line saying so. Precedence changes are always listed and counted.

With RESTACT_EXAMPLES unset the bootstrap writes no example content, so nothing is classed host-bootstrap. What this host’s own startup bootstrap writes is listed with class host-bootstrap and is not counted: the backing objects, each docs/<name> with exactly the title and document the docs directory gives, and the bootstrap verbs whose stored record equals what the bootstrap deploy writes: the route and file hash, and also the kind, limits, allowed calls, policy, grants, produces, runs_as and paused settings, with no declared data property. The match is exact. An extra anonymous object under docs/, an edited doc, a verb the bootstrap did not deploy or deployed with other options, a different hash, or a file the audit cannot read is counted, and its line names the first item that differs. A claim is also listed host-bootstrap when its ancestor is exactly such an object and every foreign descendant is a direct child of an object a bootstrap action is bound to by {id} (counters/<id> under counters), and that bound verb is stored exactly as the bootstrap deploys it; a tampered ancestor, a deeper descendant or a redeployed verb is counted.

The last line is always ancestry-audit: done (<claims> claimed ancestors, <pairs> precedence changes, <orphans> orphan definitions).

ExitMeaning
0No findings.
3At least one finding.
1The audit could not complete: the data directory holds an interrupted restore (RESTORE-IN-PROGRESS.json; finish it with restactd restore), or the store could not be read.
2Usage error; RESTACT_DATA_DIR is missing, empty, unset, has no format.json naming a format this binary reads, or lacks its blobs/ or state/ directory; or the environment is one the server refuses to start on.

The audit writes nothing, by construction: it never creates or stamps a store or a directory, uses the in-process coordinator whatever RESTACT_ISOLATION says (so it creates no locks/), keeps its own page-token key in memory (so a snapshot, a restored store or one without page-token.key or the host_keys row audits like any other), takes no data-directory lock and opens no listener. It can run beside a live server, and it can run from a one-off container or Job before a new binary starts serving. On PostgreSQL, run it from one node or one Job. Warnings the store and the registry load raise while it reads print to stderr. A host serving a store with changed pairs prints one stderr line once serving has started, warning: N same-level pattern pairs are won by the leftmost literal where literal count alone would tie or pick the other route; run restactd audit ancestry to list them.

To fix a finding, see Recovering from ancestor-claim; the remedy for a claim or an orphan is POST /admin/reown, or restactd reown when no server is running.

Move ownership offline

Section titled “Move ownership offline”

restactd reown moves the verbs and objects that one subject owns, under one path, to another subject. It is the offline door to POST /admin/reown and runs the same code, so the result is the same. It needs no running server, no bearer token and no RESTACT_ADMIN_REOWN. Use it when an owner has left and the server is down, or when no operator subject is set up.

It reads the same RESTACT_* variables as the server: RESTACT_DATA_DIR or RESTACT_DATABASE_URL, and the secrets settings. It reads no authentication setting. A real move on a terminal selects first and asks Move N verbs and M objects that alice owns under area/x to bob? [y/N]; off a terminal it refuses with exit 2 unless you pass --yes. A dry run never asks.

The server skips a verb’s secret slot when the slot lies under its secrets mount, so the command needs the same mount. Set RESTACT_SECRETS_URL and RESTACT_SECRETS_MOUNT as the server has them, or pass --no-secrets if the server runs without one. With neither, the command exits 2 before it opens the store, a dry run included. It never opens the secrets backend.

Filesystem. A real move takes the data-directory lock, so it exits 6 while a server or another command holds the directory. Stop the server first, or send the move through the running server with restact admin reown. The change goes live when a server next starts on the directory and loads the records. A dry run takes no lock and runs beside a live server. A directory with an interrupted restore is refused (exit 1) and a directory that is not a store root is refused (exit 2).

PostgreSQL. The command connects as one more node beside live servers, checks that the database schema matches this build (exit 2 if it does not), and tells the other nodes about each moved verb. It takes no data-directory lock. A reown on another node, or a deploy racing the command on a single node, can leave a window the command does not cover. Run --dry-run again afterwards: it selects nothing when the move held. A stopped cluster has no such windows.

Stdout has one line per moved item, verbs first and then objects, and a final done line; --json prints the HTTP route’s 200 body on one line instead. Stderr carries a note naming the secrets mount in effect and, for a real move, the audit line warning: admin reown by 'restactd:reown': .... Moved objects are stamped in their provenance with the subject restactd:reown and no actor. A verb’s record does not record the move.

ExitMeaning
0Done, including a dry run and a run that matched nothing.
1The move could not complete (a store error part-way, an interrupted restore, an unreachable database, or stdout could not be written).
