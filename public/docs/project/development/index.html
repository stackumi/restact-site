Development

How to build, run, test and extend restactd. If you are new to the code, read Architecture first.

Toolchain

Section titled “Toolchain”

Rust is pinned to an exact version (currently 1.99.1). mise.toml is the source of truth; rust-toolchain.toml mirrors it (plus the wasm32-wasip2 target and rustfmt/clippy) for rustup-only callers and CI, and the workspace rust-version in Cargo.toml is its major.minor; the Dockerfile builder stage’s rust: tag and digest is the fourth site. make check-toolchain-pin fails if they disagree. To bump Rust, edit all four together and fix what the new clippy reports. CI installs the pin via .github/actions/rust-toolchain, never “newest stable”. The one-time setup:

This installs (idempotently, without sudo): the Rust toolchain and wasm target, the WebAssembly component tooling (cargo-component at the version CI uses and wasm-tools at the version mise.toml pins), and the git hooks. The tools make ci and your first git commit need are pinned in mise.toml: gitleaks (the pre-commit secret scan), cargo-deny, cargo-nextest (parallel host-tests), shellcheck, node, actionlint and zizmor. When mise is installed the script runs mise install for them; without mise it lists what is missing and where to get it. A tool counts as present only when it is on PATH, because make runs it from there: if mise installed it but your shell cannot see it, the script says so and exits non-zero. Add eval "$(mise activate bash)" to your shell rc (or put mise’s shims directory on PATH) and open a new shell. The Python gates (openapi-validate, plugins-check) need PyYAML and jsonschema, which the script installs with pip when they are absent.

Formatting

Section titled “Formatting”

The repository has no auto-formatting. The Rust code is not rustfmt-formatted, and rustfmt.toml sets disable_all_formatting = true so cargo fmt and an editor’s format-on-save change nothing. A change matches the style of the code around it. .editorconfig records the indentation in use (four spaces for Rust, Python and WIT, two for shell, JavaScript, YAML and JSON, tabs in the Makefile). Clippy with -D warnings is the enforced style gate.

How long make ci takes

Section titled “How long make ci takes”

As a rough guide, on a machine with six CPUs and a warm build directory, the parts of make ci take: 1.5 minutes for the static guards, 1 to 5 for clippy and the unit tests, about 5 for restactd’s own suite (host-tests, plus about 3 for the runner and example builds it needs), 1 for cargo-deny and the secrets scan, and under 1 for the plugin lint. (host-tests runs the integration binaries concurrently under cargo-nextest.) That is about 9 to 17 minutes on an unchanged tree, and about 25 after a change to the host crate, which rebuilds the test binaries. From a cold build directory, expect about 30 minutes. A machine with fewer cores, including a standard GitHub-hosted runner, takes longer. make suites, the black-box suites, add about 35 minutes on top.

Gotchas (read these first)

Section titled “Gotchas (read these first)”
  • The host binds 127.0.0.1:8080, so run one instance at a time. Restart it by killing whatever is listening on that port (lsof -tiTCP:8080 -sTCP:LISTEN | xargs -r kill), never pkill -f target/debug/restactd, which matches by binary path and kills every restactd on the machine. Run it in the background when it must persist across steps. The black-box suites take RESTACT_TEST_PORT=<free port> (default 8080; RESTACT_CONFORMANCE_PORT is an alias for conformance-test.sh) and clean up only a restactd listening on that port.
  • The workspace members are host, host/cwasm, conformance and cli (the restact client and its MCP bridge). examples/ and sdk/ are excluded: they build for wasm32-wasip2 (with cargo-component, or plain cargo build --target wasm32-wasip2 for the SDK), not the host toolchain.
  • The JavaScript tier is interpreted, not compiled. Build the trusted QuickJS runner component once with scripts/build-js-runner.sh (needs cargo-component + the wasm32-wasip2 target; the rquickjs build fetches a WASI SDK and compiles QuickJS from C). A checkout that skips it just starts without the JS tier (discovery omits it, and an upload with ?lang=text/javascript returns 415).
  • With curl and bound-verb routes, pass {id} with -g (globoff) or URL-encoded as %7Bid%7D; otherwise curl’s glob expansion mangles the path.

Section titled “Test”

Tests are the source of truth. Most black-box scripts start their own copy of the host, so stop any running instance first.

Coverage

Section titled “Coverage”

Coverage is informational (no CI gate) and reported as two separate numbers, because a single percentage would conflate code that is verifiable in two different ways:

CommandWhat it measures
make coverageUnit line coverage of the host crate with default features, from the in-process cargo test suite (http_tests.rs and the per-module #[cfg(test)] tests).
make coverage-functionalFunctional line coverage: the host binary is instrumented (cargo llvm-cov show-env) and driven through postgres-test.sh + spike-smoke.sh, capturing the running binary and its worker subprocesses.

The optional PostgreSQL backend (host/src/pg/*.rs) and the cross-node wiring in lib.rs (open_backends / readyz / the LISTEN-loop spawners / build_worker_executor) are not unit-testable in-process, because they need a real database or a separate worker process. A real-database “unit” test would exercise Postgres, not the type under test. So the PostgreSQL backend is excluded from the unit number (make coverage builds default features, so pg/*.rs isn’t compiled) and earns its confidence as a functional percentage instead.

A module with thin or zero unit coverage must carry a correspondingly higher functional number. pg/*.rs should be near-fully covered by make coverage-functional (postgres-test.sh exercises it end to end), while a unit-heavy module like policy.rs leans on the unit number. When you add code that can only be reached cross-node or through a real database, add the assertion to the relevant black-box suite rather than reaching for a unit test that can’t exist.

Docker

Section titled “Docker”

The repo ships a self-contained multi-stage Dockerfile. The builder compiles the host plus the example verbs and both scripting-tier runners; the runtime image is a slim, non-root Debian that binds 0.0.0.0:8080 and persists to a /data volume. The image sets RESTACT_ALLOWED_HOSTS=localhost, so it answers only to localhost, 127.0.0.1 and [::1] until you override it with the names clients use.

  • The two scripting tiers are on by default. For a faster, lighter build that omits them, use make docker-build-core (--build-arg WITH_JS=false --build-arg WITH_PY=false); the host then starts without the JS/Python tiers, and ?lang=text/javascript or ?lang=text/x-python uploads return 415.
  • The first (cold) build is slow: the JS runner downloads a WASI SDK and compiles QuickJS from C.
  • Configure the container with the same environment variables as a native run; see Configuration for a Docker example and the full variable reference.
  • Release archives are built by the release workflow. make release-local VERSION=0.1.0-dev (a *-dev label, or exactly the workspace version) builds the same tarballs into dist/, smoke-tests them and runs the verify checks, and make release-images VERSION=0.1.0-dev builds the two images from them without pushing. The maintainer steps for cutting a release are in Releasing.
  • The Dockerfile build above is for development, and it targets linux/amd64. .github/workflows/docker.yml runs it on demand as a build and boot check; it publishes nothing. Released images are assembled from the release tarballs by release/image.Dockerfile; see Releasing.

Pull requests

Section titled “Pull requests”

Before you open a pull request, run make ci and the suites that cover your change. A draft pull request runs only the light CI jobs: the static guards, the plugin lint and the supply-chain scans. The docs-site build (docs-site.yml) also runs when the change touches its inputs. A pull request that is ready for review also runs the heavy jobs: clippy and the unit tests first, then restactd’s own tests and the black-box suites. Each later push runs them again, so a draft is a cheap place for work in progress.

In the public repository every CI job runs on GitHub-hosted runners: pushes, scheduled and manual runs, and pull requests, forks included. The self-hosted runners serve only a private repository and are not registered to the public one. That registration is the control; the workflow files enforce nothing, because a pull request runs its own copy of them. The runs-on expression in ci.yml only picks the runner for cost and speed, each self-hosted job opens with a step that fails if it finds itself on a non-hosted runner outside that private repository (a guard against our own misconfiguration), and make check-runner-routing keeps the expression and that step in place. The hosted runners are smaller than the self-hosted ones, so a timing-sensitive test can fail on a hosted run where it passes locally; re-run once before treating it as a regression.

A workflow run from a fork waits for a maintainer to approve it, for every outside collaborator. Read the diff, including .github/, scripts/ and Makefile, before approving: an approved run executes that code on a GitHub-hosted runner with a read-only token and no secrets.

A ready pull request skips the heavy jobs when every file it changes is on the skip-list in scripts/ci/classify-changes.sh: files under a docs/ subdirectory (except docs/guides/rust.md, which make check-rust-snippets compiles) or docs-site/, top-level docs/*.md pages, most design records in spec/decisions/, and top-level Markdown and licence files. Test hosts seed fixture pages rather than the live ones, so prose changes need no heavy run. Markdown elsewhere in the tree (for example under cli/, which the bridge embeds) and non-Markdown files directly in docs/ are not on the list.

The otel, PostgreSQL and plugin end-to-end jobs, and the MCP bridge suites inside the suites job, run only when the change touches what they test. scripts/ci/classify-jobs.sh decides this from the changed paths and, for otel and PostgreSQL, from whether a changed file contains feature = "otel" or feature = "postgres". A push to main runs every CI job.

The otel job runs only what the feature adds, not the whole suite a second time. scripts/ci/otel-tests.sh runs:

  • the lib tests that exist with --features otel and not without it (the diff of two --lib -- --list runs, computed each time, so a new otel-only test is picked up by construction and an empty diff fails the job), plus the telemetry:: and spans_tests:: modules whole;
  • each host/tests binary (about 69) whose source mentions otel in any case, every adr0100_* binary, and every binary that uses a helper module (a dir with no main.rs, such as support/) that mentions it. Binaries in scripts/ci/thread-pins.sh keep their thread pin.

Every other test already runs without the feature in host-tests.sh, and clippy --features otel --all-targets compiles every target under it. make ci-otel runs the same script, and make otel-tests-test (a static gate) self-tests the binary selection.

Suite lanes

Section titled “Suite lanes”

The suites job runs every black-box suite through one script, scripts/ci/lanes.sh, from one manifest, scripts/ci/lanes.txt; make suites runs the same pair, so local and CI runs cover the same list. make check-lanes (a static gate) fails when a scripts/*-test.sh suite is missing or listed twice, a fixed-port or shared-binary suite (the restact mcp suites, cli-test.sh, plugins-e2e.sh) is outside lane C, or the lane port blocks overlap. A new suite goes into the manifest or, with a reason, into the exclusion list in scripts/ci/test-lanes.sh.

SettingMeaning
RESTACT_LANES=1 (default)every entry serially, in manifest order, on port 9171.
RESTACT_LANES=3the warmup entries first (the cargo builds, spike-smoke, the restact build variants; a failure stops the run), then lanes A, B and C concurrently on port blocks 9181, 9191 and 9201, each with its own TMPDIR under <base>/<lane>/tmp; <base> is $RUNNER_TEMP/lanes in CI and a fresh mktemp -d "$TMPDIR/lanes.XXXXXX" (printed) locally.
repository variable RESTACT_CI_LANESCI’s value for RESTACT_LANES (unset means 1).
RESTACT_LANES_ONLY=a,b, RESTACT_LANES_DRY_RUN=1run only those labels; print the plan (lane, port, TMPDIR, command) and exit.
RESTACT_GATE_MCP, RESTACT_GATE_PLUGINS_E2Efalse skips a gated entry. MCP runs unless false (CI passes the classifier’s result). The plugins-e2e entry runs only when its gate is true (default off, so make suites does not start it; CI runs plugins-e2e as a job of its own).
RESTACT_LANES_TIMEOUTper-suite timeout in seconds (default 1200, sized for a cold debug build in warmup).

No suite stops its lane at the first failure; the step fails if any suite failed or did not run. Each suite’s log is replayed in a collapsible group, a failure adds an error annotation with its last FAIL lines, the step summary lists wall time and CPU-throttling per suite, and a FAIL line mentioning 408 adds a warning (a likely sign that the host was starved of CPU). The lane logs (*.log, *.rc, *.secs; no data directories) are uploaded as the suite-lanes artifact for 7 days when the step fails, is cancelled or times out. Serial mode streams live. Local runs use ports 9171-9174, 9181-9184, 9191-9194 and 9201-9204, and the cleanup after each suite SIGTERMs a restactd listening on them, so do not hand-run a suite on those ports meanwhile. RESTACT_LANES_PORTS="warmup=N A=N B=N C=N" moves the blocks (the runner self-test uses 39171 and up). A suite that turns flaky only under lanes is moved to another lane or given a looser wall-clock margin, never retried.

To try lanes on CI without changing the variable, run ci.yml by hand with its lanes input (gh workflow run ci.yml -f lanes=3); the input wins over the variable for that run only.

Conventions & constraints

Section titled “Conventions & constraints”
  • The WIT package rest-act:plugin@0.1.0 (wit/) becomes frozen at the first public release, or earlier if the maintainer declares it. Until then a change needs the maintainer’s approval, and a breaking one lands as a single change set across every component built against the package, including host/wit/, the packaged copy the host compiles against; make check-host-wit fails when it differs from wit/. New capabilities arrive as new, individually gated worlds and interfaces. See WIT interfaces.
  • openapi/x-restact-extension.schema.json is additionalProperties: false. Extend it through new $defs, then run the validator.
  • Design decisions are recorded in spec/decisions/, indexed in its README. When you make a non-obvious design decision, add or extend a record. Deferred work is a GitHub issue.
  • In the RESTACT_WORKER subprocess path, only the response goes to stdout. All diagnostics use eprintln! (stderr); never println! on that path.
  • Optional features are discovery-gated. Advertise them in service.features; a verb may require a feature, and the host returns 501 if it is unsupported. Keep new features optional and advertised.
  • Extend scripts/spike-smoke.sh (fast, local) and the conformance suite whenever observable behavior changes.
