FAQ

Short answers to the questions people ask first, with a link to the page that has the detail.

Is restactd production ready?

Section titled “Is restactd production ready?”

Not yet. The HTTP surface can still change before 1.0. The WIT package that verbs compile against freezes at outside adoption, the first public release or earlier if the maintainer declares it. See Status and roadmap for what freezes and what can still change, and the Production checklist if you run it anyway.

What is a verb?

Section titled “What is a verb?”

A small WebAssembly program, or a JavaScript or Python script that the host interprets, uploaded over HTTP and called at a URL. GET /v1/docs:summarize calls a function, which cannot change state. POST /v1/pages/home:visit calls an action, which can. See The model in one page.

How is this different from serverless functions?

Section titled “How is this different from serverless functions?”

A serverless platform deploys code for its operator, usually through a separate build and release pipeline, and the function runs with its own service identity. In restactd the client uploads the verb through the same HTTP API it calls, the verb is bound to a path in the object tree, and it runs as the caller: it can read and write only what the caller could. The comparison with other approaches is in the specification repository.

How is it different from Spin or wasmCloud?

Section titled “How is it different from Spin or wasmCloud?”

Spin and wasmCloud run WebAssembly components that an operator deploys and routes. restactd is a server for the REST:ACT protocol: verbs are uploaded by API clients at runtime, addressed as object:verb, tied to stored object data, and subject to per-object access policy, one shared budget across composed calls, and discovery-advertised features. Pick by who deploys the code and who it runs as.

How is it different from Extism?

Section titled “How is it different from Extism?”

Extism is a plug-in system for an application: the application’s developers pick the integration points and its users or customers supply the plug-ins, which the application loads through an Extism host SDK. restactd is a standalone server with that upload path built in. Clients upload verbs over HTTP, and each verb is bound to an object path, runs as the caller and shares one budget when verbs call each other. Extism gives you a plug-in runtime to embed; restactd gives you a protocol and a server.

How is it different from PostgREST or Supabase?

Section titled “How is it different from PostgREST or Supabase?”

PostgREST exposes Postgres functions over HTTP: POST runs any function, GET runs one that does not modify the database. That is close to restactd’s function and action split. The code is different, though. A PostgREST function is a Postgres function created in the database schema by someone with database access, and access follows database roles. A restactd verb is uploaded over HTTP at runtime in WebAssembly, JavaScript or Python, runs in a sandbox with fuel, time and memory limits, and sees only the capabilities its world grants. Supabase builds on PostgREST, and its own path for custom server code is Edge Functions: TypeScript on Deno, deployed with the Supabase CLI or dashboard and running on Supabase’s Edge Runtime, outside the database. Use PostgREST when the database is the application; use restactd when clients should be able to add behavior to a running server.

How is it different from Hasura actions?

Section titled “How is it different from Hasura actions?”

A Hasura action is a GraphQL field backed by a REST endpoint you provide, whether your own server, a public API or a serverless function. Hasura routes the call; your service runs the code. In restactd the host itself runs the code, in its sandbox, and the code arrives over the same HTTP API that calls it.

How is it different from PocketBase hooks?

Section titled “How is it different from PocketBase hooks?”

PocketBase hooks are JavaScript files, *.pb.js, that the operator places in a pb_hooks directory beside the executable. They run in an embedded interpreter as the application’s own code. restactd verbs are uploaded by API clients at runtime, bound to object paths and confined by capabilities, and the JavaScript tier is one of three language tiers.

How is it different from Cloudflare Workers for Platforms?

Section titled “How is it different from Cloudflare Workers for Platforms?”

Workers for Platforms lets a platform run its customers’ code, each customer in its own isolated Worker on Cloudflare’s network. The problem is close to restactd’s, running code you do not trust, but it is a hosted service built around separate Workers per customer. restactd is software you run yourself, where uploaded verbs live in one object tree, run as the calling user, and can compose under one shared budget.

Which languages can I write verbs in?

Section titled “Which languages can I write verbs in?”
  • Rust, with the restact-sdk crate, compiled to a wasm32-wasip2 component. See Write verbs in Rust.
  • JavaScript, uploaded as source and run by an embedded QuickJS runner. See Write verbs in JavaScript.
  • Python, uploaded as source and run by an embedded interpreter. See Write verbs in Python.
  • Any other language that can produce a component for the rest-act:plugin WIT package. See WIT interfaces.

Language tiers compares them.

Can a verb make network calls?

Section titled “Can a verb make network calls?”

No. No world gives a verb sockets or a usable filesystem, and an uploaded verb cannot make an HTTP request. The one outbound path a verb has is the llm capability: the verb asks for a text completion, and the host sends it through an operator-configured connector that holds the credential. General outbound HTTP calls with stored credentials are available to Rust code that embeds restactd. See Outbound calls and secrets.

How is untrusted code contained?

Section titled “How is untrusted code contained?”

Each call runs in a Wasmtime sandbox that can reach only the host functions its world imports. Fuel, wall-clock time and memory are limited per request; the defaults are 200,000,000 fuel units, 2 seconds and 32 MiB, and an uploader can ask for less or more only up to the operator’s ceilings. Optionally each request runs in a separate worker process. See Capabilities and budgets and the Security model.

What does a call cost?

Section titled “What does a call cost?”

Every call has a budget and is metered, so cost is bounded and visible. Composed calls draw from one shared budget, and per-tenant quotas can cap invocations and compute over a window. A call that runs out returns 429 (fuel or quota), 408 (time) or 507 (memory); see Errors and status codes. Metrics and traces are covered in Observability.

Does it scale horizontally?

Section titled “Does it scale horizontally?”

Yes, with the PostgreSQL backend. Several stateless nodes behind a load balancer share one database. Without it the host keeps state in memory or in a local directory, which suits one node. A binary needs the postgres Cargo feature for this. See Storage and scaling.

Where does it store data?

Section titled “Where does it store data?”

In memory by default, which is lost on restart. Set RESTACT_DATA_DIR for a durable local store, or RESTACT_DATABASE_URL for PostgreSQL. See Configuration.

Can I embed it in my own Rust application?

Section titled “Can I embed it in my own Rust application?”

Yes. The host is a library as well as a binary. You can add your own trusted native verbs and HTTP routes next to the uploaded ones. See Embed restactd in a Rust app.

How do AI agents use it?

Section titled “How do AI agents use it?”

Through the same HTTP API, through a built-in MCP endpoint at /mcp that the operator can turn on, or through the restact mcp bridge, which turns a host’s discovery document into MCP tools. An agent can deploy a verb, call it, and read its descriptor. See Use restactd from AI agents.

How do I know a server behaves correctly?

Section titled “How do I know a server behaves correctly?”

Run the conformance suite against it. It reads the discovery document, checks the mandatory core, and checks each optional feature the server advertises. See Conformance suite.

Can I run a different server that speaks REST:ACT?

Section titled “Can I run a different server that speaks REST:ACT?”

Yes. restactd is the reference implementation of the protocol, and the protocol is specified separately in the Specification repository. A client should rely only on what discovery advertises.
